# Playbook Artifact Transition Inventory

This inventory is the FEAT-011 handoff for later hardcoded-pipeline migration work. It records the artifact completion transitions in the eight named services without changing those services.

## Terms and ordering rule

A **cross-process arbiter** is durable state checked at the final write that identifies the active run, such as an artifact row's thread ID combined with its current status. An in-memory watcher map, thread-id parameter, or process-local applied set is not enough.

Future extraction order follows all three rules:

1. **Eligibility:** extract a transition only when it has a cross-process arbiter. If it does not, building and testing that arbiter is the first task of the extraction.
2. **Upstream before downstream:** never extract a downstream artifact transition before every transition that starts or unblocks it.
3. **Ascending blast radius:** among eligible transitions whose upstream dependencies are complete, extract the transition with the fewest downstream consumers first. Ties sort by service path, then transition name. Watcher size does not affect order.

The dependency graph must remain acyclic. A cycle or an unverified edge blocks publication of a revised order.

## Candidate extraction order

FEAT-010 validation transitions are already extracted and are not future candidates. For the remaining transitions, the deterministic candidate order is:

1. **ADR generation** — independent, blast radius 2; build its stored-thread arbiter first.
2. **Design Module regeneration** — independent, blast radius 2; build active-regeneration identity first.
3. **Feature Request analysis** — independent, blast radius 2; complete its thread-qualified terminal writes first.
4. **Walkthrough Anchor smart tagging** — independent, blast radius 3; add durable once-per-batch application first.
5. **PRD generation** — pipeline root despite blast radius 4; it must precede all PRD-derived transitions.
6. **Design Prototype generation/regeneration** — now upstream-complete, blast radius 2; add durable generation identity first.
7. **Single-feature Design Doc generation** — follows PRD and prototype generation where applicable, blast radius 2.
8. **Multi-feature Design Doc generation** — follows PRD generation, blast radius 3; consolidate child creation under one arbiter.
9. **Test Case generation** — follows PRD generation, blast radius 4; tighten its final conditional write before extraction.

The order places independent equal-radius candidates by service path/name only after applying their arbiter-first prerequisites. Test Case generation appears after the Design Doc candidates because its four durable consumers/effects give it the larger blast radius; this does not violate an upstream edge between those sibling branches.
