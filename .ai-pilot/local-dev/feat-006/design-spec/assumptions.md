# Assumptions & Unresolved Items — Host-Agnostic Work-Item Integrate

> Shared between [design-doc-design.md](design-doc-design.md) and [design-doc-tech-spec.md](design-doc-tech-spec.md).
> Resolve all ⚠ items before implementation begins.

---

## Unresolved Items

- ⚠ **Who actually opens the pull request the Cloud Agent produces**: The PRD's implementation decision for the webhook completion receiver (FEAT-001) says the receiver "hands the mapped status, **PR URL**, branch, and summary to the run lifecycle service's terminal write" — read literally, the PR already exists by the time Apex hears about it, i.e. the vendor Cloud Agent opens it directly against the code host. This blocks TBI-008's core design choice: if the vendor creates the PR, Apex can only *instruct* the agent (via its run prompt) to embed the GitHub `AB#{workItemId}` mention and can only *verify after the fact*; if Apex itself creates the PR (reusing `createSessionPr`'s pattern in `src/server/routes/devWorkbench.ts`, the same way it already does for local dev sessions), the embedding is deterministic and no verification step is needed at all. This design doc and tech spec proceed on the **vendor-creates-the-PR** reading because it is the more explicit, more recently stated architecture decision in the PRD, but the team must confirm this against FEAT-001/FEAT-002's own tech specs (not generated in this run) before implementation starts. If the confirmed answer is "Apex creates the PR," TBI-008 shrinks to "extend `createSessionPr`'s existing AB#/`workItemRefs` logic to the Cloud Agent branch" and the new verification functions in this spec (`verifyGithubReference`, the GitHub `getPullRequest` export) become unnecessary.
- ⚠ **Can the vendor Cloud Agent authenticate against Azure Repos at all**: The epic's own assumptions explicitly defer "Verifying Azure Repos as a Cloud Agent launch target beyond accepting the `skillProvider` values Project Skill Settings already supports" as out of scope. That means it is unconfirmed whether the sandboxed Cloud Agent is even capable of pushing to, or opening a PR against, an Azure Repos-hosted skill repository, let alone attaching a native work-item link itself. This design treats Apex's own server-side ADO connection (`AzureDevOpsService`) as the sole guaranteed writer of the native work-item link (see Assumptions Accepted below), which sidesteps the question but does not resolve it — the underlying capability question belongs to FEAT-001/FEAT-002 and should be confirmed there before this Feature ships.
- ⚠ **Exact Azure DevOps API for linking a work item to an *already-created* pull request**: `AzureDevOpsService.createPullRequest()` (`src/server/services/azureDevOps.ts:5932`) already sets `workItemRefs` on the payload passed to `gitApi.createPullRequest`, but that only works at PR-creation time. This Feature needs the equivalent for a PR that already exists (created by the vendor). The Azure DevOps REST surface exposes a "Pull Request Work Items" endpoint for this (`PUT .../git/repositories/{repositoryId}/pullRequests/{pullRequestId}/workitems/{workItemId}`), but no code in this repository calls it today, and the exact method name on the installed `azure-devops-node-api` `IGitApi` client version has not been confirmed. `AzureDevOpsService.linkWorkItemToPullRequest()` in the tech spec is named as a placeholder for this call; confirm the SDK method signature against the installed `azure-devops-node-api` version before implementation.
- ⚠ **Destination for the "missing AB# mention" log signal**: TBI-008's non-functional requirement says missing references must be "logged so they can be detected without a manual audit." The closest existing precedent (`devWorkbench.ts`'s `cascadeChildStates` and its PR-creation try/catch) uses plain `console.warn`, which satisfies "not silently dropped" but is not queryable without log aggregation tooling. Whether this needs to escalate to a structured, queryable signal (e.g. a `workerTierTelemetry`-style event, or a row surfaced through FEAT-005's leftover-work summary) is not specified in the PRD or backlog. This spec defaults to `console.warn` for parity with the closest existing pattern and calls out promotion to a structured event as an optional follow-up (see Observability in the tech spec).

## Assumptions Accepted

- **Vendor-creates-the-PR reading drives a verify-for-GitHub / write-for-Azure-Repos split**: Because the vendor Cloud Agent's own PR-creation call is outside Apex's control, this design treats GitHub's `AB#{workItemId}` mention as agent-instructed-and-verified (Apex reads the resulting PR back and logs if the mention is missing, per PBI-009 AC (b)'s "treated as a defect... logged" wording), while Azure Repos' native work-item link is Apex-guaranteed (Apex's own `AzureDevOpsService` calls a new post-hoc link API immediately after the webhook reports the PR URL, per PBI-009 AC (c)'s unconditional wording with no "logged if missing" caveat). Risk if wrong: if Apex turns out to own PR creation entirely, this asymmetric verify/write split is unnecessary complexity and should collapse to a single deterministic write path.
- **Single shared module owns the mention/link logic for both dev-workbench flows**: The AB# mention text and Azure Repos `workItemRefs` linking already live inline inside `createSessionPr()` in `src/server/routes/devWorkbench.ts` for the existing local-dev PR flow. This design extracts that logic into a new `src/server/services/workItemPrLinkService.ts` so both the existing local-dev path and the new Cloud Agent outcome-writer path call the same functions instead of maintaining two copies of the mention convention. Derived from the "reusing the existing ADO write path already used for PR creation on this router" language in the PRD's implementation decisions. Risk if wrong: low — this is a refactor-for-reuse decision, not a behavior change to the existing local-dev flow.
- **No new RBAC permission or client-facing route**: TBI-008 is a server-to-server step inside the already-authenticated webhook completion path; it introduces no user-invoked action and no new permission key, consistent with the PRD's own assumption "No new RBAC permission key is introduced." Derived from PBI-009's own NFRs, none of which describe a new endpoint, and from the epic's stated exclusion of any new permission key. Risk if wrong: negligible — if a future audit surface for missing references is added, it would read existing run/session data already gated by `dev-workbench:view` and author-only scoping, not introduce a new gate.
- **No database migration**: This Feature reads and writes only external system state (the PR on GitHub/Azure Repos, the work item in Azure DevOps) plus the run/session PR fields TBI-001 (FEAT-001) and TBI-006 (FEAT-004) already add. Derived from TBI-008's description and definition of done, which name no new table or column. Risk if wrong: low — if a leftover-work-style "reference verified" flag needs to persist, it would extend TBI-006/TBI-007's existing session/run fields rather than introduce a new table.
- **Target surface is backend-only for this Feature specifically**: Although the parent PRD's overall target surface is full-stack, PBI-009's own UI/UX-related NFR states accessibility is "Not applicable — the work-item reference lives in PR title/body text on the git host, not in Apex UI." Derived directly from that NFR. Risk if wrong: none identified — no AC or business rule for this Feature references an Apex UI element.
