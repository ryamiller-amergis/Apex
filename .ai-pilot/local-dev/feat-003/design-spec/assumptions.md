# Assumptions & Unresolved Items — Server-Authoritative Effort Resolution at Kickoff

> **PRD slug:** `per-module-agent-effort-defaults` | **Priority:** Must Have | **Feature flag:** `None`
> Shared between [design-doc-design.md](design-doc-design.md) and [design-doc-tech-spec.md](design-doc-tech-spec.md).
> Resolve all ⚠ items before implementation begins.

---

## Unresolved Items

- ⚠ **Module identity for the generic chat-kickoff route**: `POST /api/chat/threads` (`src/server/routes/chat.ts`) is the single client-facing endpoint used to start Interview threads, ADR-interview threads, and every Agent Home thread (free chat, skill pill, MCP pill) — the browser supplies the full `kickoff` object, including `skillPath`, for all three. There is no existing field that already distinguishes "Interview kickoff" from "ADR-interview kickoff" from "Agent Home pill pointed at the same skill file." This blocks a literal reading of TBI-005 ("each calling service... sets a server-only module identifier"), since this one route serves three callers. **Default taken in this spec:** the route derives `agentModule` server-side by matching the resolved `ProjectSkillConfig`'s own `interviewSkillPath` / `adrInterviewSkillPath` (or the selected `InterviewSkillOption.path`) against `kickoff.skillPath`; no match (Agent Home) leaves `agentModule` unset so resolution falls through to `defaultEffort`. This is exactly as trustworthy as `skillPath` already is today (it is the same string that determines which skill file the agent actually loads), so it introduces no new spoofing surface beyond what already exists for `model`. Confirm this heuristic is acceptable, or decide whether Interview and ADR-interview should instead move off the shared route onto two thin dedicated endpoints that hardcode `agentModule` outright.
- ⚠ **ADR Assistant has no dedicated effort column**: `ProjectSkillConfig` has `designDocAssistantModel` and `prdAssistantModel` but no `adrAssistantModel` — ADR Assistant threads (`assistantType: 'adr'`, built in `src/server/routes/adr.ts`) already reuse `adrModel`. **Default taken in this spec:** ADR Assistant reuses `adrEffort` (the same FEAT-001 column ADR-interview uses) rather than requiring a new column. Confirm this matches the intended FEAT-001 column list, since TBI-001's DoD does not call out a distinct ADR-assistant stage.
- ⚠ **Cursor SDK reasoning-effort parameter shape is unverified**: this spec assumes `Agent.create`/`Agent.resume` (`src/server/services/interactiveActorHost/interactiveCursorExecution.ts`, `src/server/services/aiRunsWorker/cursorExecution.ts`) accept an `effort` argument alongside `model: { id }`, taking exactly `'low' | 'medium' | 'high'`. This mirrors the PRD's own stated assumption and must be confirmed against the installed `@cursor/sdk` version before TBI-005 implementation starts; if the real parameter name, nesting, or allow-list differs, the shared `EffortLevel` type and the SDK call sites in the two files above must be corrected to match.
- ⚠ **Agent Home skill pills and MCP pills — no module-override tier**: Agent Home threads have no corresponding `*Effort` column on `project_skill_settings` (there is no "chat" or "agent-home" stage in FEAT-001's column list). **Default taken in this spec:** resolution for these threads is pill/option effort (once `QuickSkillPill.effort` / `QuickMcpPill.effort` exist per TBI-001) → `defaultEffort` → omit, skipping the module-override tier entirely. Confirm no per-module tier is intended for Agent Home before implementation.
- ⚠ **Development and Standup coverage inside TBI-005**: `mode: 'development'` and `mode: 'standup-*'` kickoffs are built server-side (`devSessionSetupService.ts`, `standupService.ts`) but are not among the two representative modules TBI-005's DoD calls out (Interview, ADR) for direct test coverage. **Default taken in this spec:** every server-side kickoff builder — including Development and Standup — gets the same one-line `agentModule` literal as part of this feature, since the change is mechanical and low-risk once the resolver exists, but only Interview and ADR get dedicated new tests per the DoD; the rest are covered by the resolver's own unit tests plus a generic assertion that `createThread` never throws when `agentModule` is set. Confirm this scope boundary (implement everywhere, test two) is acceptable rather than deferring the other callers to a follow-up change.

## Assumptions Accepted

- **Central resolver lives in a new, focused file**: `src/server/services/agentEffortResolver.ts` is added as a new deep module (mirroring the existing pattern of small, focused services like `agentRunAbort.ts` next to the 6,500-line `chatAgentService.ts`) rather than growing `chatAgentService.ts` further. Derived from the PRD's own framing of the kickoff/config-resolution logic as "the single authority for effort," which favors one narrow, well-tested module over scattering resolution logic across call sites the way `model` resolution is scattered today (`adr.ts`, `interviews.ts`, `designDocService.ts` each repeat `skillConfig?.xModel ?? ... ?? getDefaultModel()` inline). Risk if wrong: a reviewer expects the resolution logic inline in `chatAgentService.ts` instead; low risk since the public entry point (`createThread`/`sendMessage`) is unchanged either way.
- **Effort is frozen once at `createThread` time, never re-resolved per turn**: `resolvedKickoff.effort` is computed once inside `createThread` and stored on `state.thread.kickoff`; `sendMessage` and the interactive-actor turn builders read `state.thread.kickoff.effort` verbatim and never accept a per-turn effort argument (there is no `effort` field on `SendMessageRequest`). Derived from BR-004 ("stays fixed for an in-flight conversation even if the default changes later") and from the observed asymmetry that `model` *does* support a per-turn override (`modelOverride` in `sendMessage`) while effort explicitly must not. Risk if wrong: negligible — this is stated directly in the PRD and backlog.
- **No new RBAC permission key**: per-module "who can start this module" permissions (e.g., `adr:create`, `interviews` create path, `chat:create`) are unchanged; effort resolution is a data-plane concern, not an access-control gate. Derived from the PRD's explicit Out-of-Scope line ("New RBAC permission keys — writes stay on `admin:roles`; runtime apply and audit/cost reads stay on each module's existing permissions") and confirmed against `.cursor/rules/rbac-governance.mdc`'s permission catalog, which has no per-module effort entries. Risk if wrong: none — explicitly stated in the PRD.
- **Corrupted/unrecognized stored effort values never throw**: the resolver applies a closed-allow-list type guard (`isEffortLevel`) and treats anything else — including legacy `null`, empty string, or a hand-edited row — as "unset," falling through the remaining resolution tiers. Derived from BR-005 verbatim. Risk if wrong: none — explicitly stated in the PRD.
- **FEAT-001's shared `EffortLevel` type and `project_skill_settings` columns are a completed, in-place dependency**: this spec does not redesign the columns, the shared union, or the admin write/read path (FEAT-001/FEAT-002 own those). `agentEffortResolver.ts` simply reads `ProjectSkillConfig[<module>Effort]` and `ProjectSkillConfig.defaultEffort`, both assumed already present and typed as `EffortLevel | null` by the time TBI-005 ships, consistent with the backlog's `dependsOn: ["FEAT-001"]`. Risk if wrong: TBI-005 cannot compile or ship until FEAT-001 lands; sequencing risk only, not a design risk.
- **`ChatThreadKickoff.agentModule` and `.effort` are documented as server-set-only fields**: both are typed as optional on the shared `ChatThreadKickoff` interface (so server code across `chatAgentService.ts`, `adr.ts`, `interviews.ts`, etc. can set them), but the JSDoc explicitly marks them "server-set; any client-supplied value is discarded," and no client code (`InterviewChatView.tsx`, `AdrChatView.tsx`, `ChatAgentPanel.tsx`, `StartChatModal.tsx`) is changed to populate them. Risk if wrong: a future contributor could start setting these fields client-side without a lint rule catching it; mitigated by the explicit route-level overwrite in `chat.ts` regardless of what the client sends.
