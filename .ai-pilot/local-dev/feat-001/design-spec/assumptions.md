## Unresolved Items

- ⚠ **Cursor SDK effort allow-list not independently verified**: The PRD asserts the Cursor SDK's effort argument accepts exactly `low` / `medium` / `high`, and the backlog and this Feature hard-code that exact three-value union into the database migration (`CHECK`-free `TEXT` columns) and into the new shared `EffortLevel` type. No existing code in the repository references an "effort" concept today (confirmed by repository search), so there is no prior art in this codebase to cross-check the PRD's claim against, and this sandboxed review has no way to call the live Cursor SDK to confirm its actual accepted values (e.g. whether it also accepts a `minimal` tier, uses different casing, or a different parameter name entirely). **Impact:** if the SDK's real allow-list differs, TBI-001's shared type and every column this Feature adds are wrong and require a corrective migration plus a shared-type change before FEAT-002/FEAT-003 can build on top of them. **Decision needed:** a developer with Cursor SDK access must confirm the exact literal set the SDK's effort parameter accepts before this Feature's migrations are applied to any shared environment. **Default used below:** this design and tech spec proceed with the PRD's stated `low` / `medium` / `high` (+ `null` = inherit) exactly as specified, since that is the only allow-list documented anywhere in the PRD, backlog, or codebase.

## Assumptions Accepted

- **Dedicated shared-type file for `EffortLevel`**: The new closed union lives in a new `src/shared/types/effort.ts` file rather than being added inline to `src/shared/types/projectSettings.ts`. Derived from the precedent of `ApprovalMode` in `src/shared/types/approvals.ts` — a small, cross-cutting union consumed by project settings *and* multiple artifact/usage domains, kept in its own file specifically to avoid forcing every consumer to import the entire project-settings type surface. **Risk if wrong:** low — this is a pure organizational choice; moving the type later is a mechanical, non-breaking refactor (import path change only).

- **No DB-level `CHECK` constraint on any new effort column**: Every new `*_effort` / `effort` column is plain nullable `TEXT`, mirroring the existing `*_model` / `model` columns (which are also unconstrained at the DB level and validated dynamically against `AGENT_MODELS`/`fetchAvailableModels()` in application code, not a DB constraint). This deliberately diverges from the `approval_mode` column, which *does* carry a `CHECK (approval_mode IN (...))` constraint. Derived from BR-005 ("an unknown or corrupted stored effort value at run time is treated as unset ... rather than failing the run") — that business rule only makes sense if the schema *permits* a corrupted value to exist in the first place; a `CHECK` constraint would make BR-005's own test scenario (a legacy/manually-edited row with a bad value) impossible to construct via normal SQL. **Risk if wrong:** low-to-medium — if the team later wants defense-in-depth at the DB layer, a `CHECK` constraint can be added in a follow-up migration without touching application code, since application-level validation (FEAT-002's admin write path) is the authoritative gate regardless.

- **`.$type<EffortLevel>()` Drizzle annotation on every new column**: Unlike the existing untyped `text('model')` columns, every new effort column uses Drizzle's `.$type<EffortLevel>()` generic. This is compile-time-only — it does not add a runtime cast, a Zod check, or a DB constraint, and a corrupted legacy string still round-trips through Drizzle as a plain string at runtime exactly as BR-005 requires. Derived from BR-003's requirement for a *closed* allow-list (stronger than model's dynamically-fetched, open list), which the shared type should reflect everywhere it's read. **Risk if wrong:** none at runtime; worst case is a compile-time-only inconvenience if the SDK's real allow-list differs (see the Unresolved Item above), which would require updating the type definition regardless of whether `$type<>()` is used.

- **Three separate migration files, one per TBI, shipped together**: TBI-001 (`project_skill_settings`), TBI-002 (five artifact tables), and TBI-003 (`ai_usage_events`) each get their own migration file rather than one combined file. Derived from the `postgresql-migrations` skill's guidance that dependent migrations ship in the same PR (these share the `EffortLevel` type dependency but touch disjoint tables with no FK relationship between them), and from existing precedent of small, single-purpose migration files in this repo (e.g. `20260727210000_design-module-scoping-skill-settings.sql`). **Risk if wrong:** none — this is purely an authoring/review convenience; a single combined file would apply identically.

- **Column-to-stage mapping cross-checked against the live schema, not just PRD prose**: TBI-001's description lists 19 stage names; this was cross-verified against the actual 19 existing `*Model` columns on `project_skill_settings` in `src/server/db/schema.ts` (interview, prd, adr, designDoc, designDocAssistant, designPrototype, testCase, designDocValidation, prdAssistant, prdValidation, development, standup, featureRequest, technical, issue, calendarAssistant, loadTestGeneration, designModule, designModuleScoping) plus `defaultModel` — confirming exactly 20 new nullable columns are needed, matching 1:1 with the existing model columns. **Risk if wrong:** none — this was a direct code cross-check, not an inference.

- **`design_prototypes.effort` is unconstrained at the schema layer**: TBI-002's "for the agent-engine path" qualifier is an application-level write-time rule for FEAT-004, not a schema-level constraint — `design_prototypes` has no `prototypeEngine` column of its own (that setting lives on `project_skill_settings`), so there is no row-level way to express this scoping in DDL even if desired. This mirrors how `design_prototypes.model` itself carries no engine-based constraint today (the Bedrock-path model ID lives on a separate `project_skill_settings.designPrototypeBedrockModelId` column). **Risk if wrong:** none — this is the only technically expressible interpretation given the existing table shapes.

- **Consumer-facing request/response types are explicitly untouched by this Feature**: `ProjectSkillConfig`, `UpsertProjectSkillConfigRequest`, `ProjectSkillConfigResponse` (in `projectSettings.ts`), `RecordUsageInput`/`AiCostEvent` (in `aiCostAnalytics.ts`), and the kickoff/config-resolution service (`chatAgentService.ts`) are **not** modified here. Derived directly from TBI-001/002/003's Definition of Done, which lists only the migration, `schema.ts`, the new shared type, and `InterviewSkillOption`/`QuickSkillPill`/`QuickMcpPill` — the admin read/write surface is explicitly TBI-004's job (FEAT-002) and kickoff resolution is TBI-005's job (FEAT-003). **Risk if wrong:** none — extending this Feature's scope to those files would violate the backlog's own dependency ordering and duplicate work FEAT-002/FEAT-003 are chartered to do.

- **No new RBAC permission, endpoint, or index**: Matches the epic's explicit Out-of-Scope ("New RBAC permission keys," "New skill files, new services, or new SSE event/streaming types") and TBI-001/003's NFRs ("No new index"). This Feature is additive DDL and shared-type-only, with zero new runtime surface. **Risk if wrong:** none — directly stated in the PRD.
