# Assumptions & Unresolved Items — Configure Home Pill Allow-Lists

> **PRD slug:** `home-pill-access-control` | **Priority:** Must Have | **Feature flag:** `None`
> Shared between [configure-home-pill-allow-lists-design.md](configure-home-pill-allow-lists-design.md) and [configure-home-pill-allow-lists-tech-spec.md](configure-home-pill-allow-lists-tech-spec.md).
> Resolve all ⚠ items before implementation begins.

---

## Unresolved Items

- ⚠ **Deployment sequencing with FEAT-002 (public `GET /api/skill-config` exposure window)**: `TBI-001` adds `allowedUserIds`/`allowedGroupIds` to `QuickSkillPill`/`QuickMcpPillBase`, and the existing `GET /api/skill-config` handler (`src/server/routes/api.ts`, ~line 4333) already returns `quickSkillPills`/`quickMcpPills` **verbatim** (`config.quickSkillPills ?? null`) to any session-authenticated caller, with no per-field allow-list. Stripping `allowedUserIds`/`allowedGroupIds` from that response is explicitly TBI-004's job in **FEAT-002 (Enforce Home Pill Access)**, not this Feature. Because this Feature has no feature flag (`None`, per the PRD) and stores the new fields inside the same JSON pill arrays that endpoint already returns wholesale, **if FEAT-001 ships to production before FEAT-002's TBI-004 lands, any authenticated user can see who is/isn't allow-listed on a pill** by calling `GET /api/skill-config?project=X` — the exact private data the PRD's "Security and Data Sensitivity" section says must never reach that response. This blocks whether FEAT-001 can be released independently. **Recommended default (applied in this spec): No.** Treat FEAT-001 and FEAT-002's TBI-004 as a single deploy unit — merge/release them together, or hold FEAT-001's merge until TBI-004 is ready to ship in the same release. Confirm this release-sequencing constraint with the engineering owner of the FEAT-001/FEAT-002 rollout before either ships.
- ⚠ **Validation depth for allow-list identifiers at the write endpoint**: The PRD's own "Assumptions Made" section states allow-list entries are "validated only for being well-formed identifiers" and flags this for confirmation with the admin experience owner. `POST`/`PUT /api/admin/project-settings` (`src/server/routes/admin.ts`) already accepts `quickSkillPills`/`quickMcpPills` as opaque arrays with zero per-field validation today (mirrors `skillPath`, `mcpServerName`, and existing approver IDs) — `projectSettingsService.upsertSkillConfig` persists `opts.quickSkillPills ?? null` unchanged. This blocks whether TBI-001/TBI-002 need a new validator (e.g. a `validateAllowListFields()` mirroring the existing `validateEffortFields()` in `admin.ts`) to defend a caller hitting the write endpoint directly, bypassing `GroupAwarePeoplePicker` (which only ever emits real `oid`/group-`id` values already present in `allUsers`/`groupsWithMembers`). **Recommended default (applied in this spec):** no new server-side validator — accept any string array, identical to every other pill field's current validation depth. Confirm with the admin experience owner if defense-in-depth against a raw API call is required.

## Assumptions Accepted

- **No database migration**: `allowedUserIds`/`allowedGroupIds` are added only to the shared `QuickSkillPill`/`QuickMcpPillBase` TypeScript interfaces. They live inside the existing `quick_skill_pills`/`quick_mcp_pills` `jsonb` columns on `project_skill_settings` (`src/server/db/schema.ts`, lines 823–824), which are already typed generically as `$type<QuickSkillPill[]>()`/`$type<QuickMcpPill[]>()`. Derived directly from TBI-001's Definition of Done and the PRD's Implementation Decisions. **Risk if wrong:** none identified — this is explicit in both the PRD and backlog.
- **No new route or service change for persistence**: `router.post('/project-settings')` and `router.put('/project-settings/:id')` in `admin.ts` already spread the full request body (`{ ...body, ... }`) into `projectSettingsService.upsertSkillConfig`, which stores `quickSkillPills`/`quickMcpPills` as opaque arrays. Adding two optional keys inside each pill object requires no route or service code change — only the shared type needs to carry them, identical to how the `effort` field was added to the same interfaces in the prior `per-module-agent-effort-defaults` epic. **Risk if wrong:** low — verified directly against `admin.ts` and `projectSettingsService.ts` source.
- **No new RBAC permission key**: Writes reuse the existing `admin:roles` gate already applied at the router level (`router.use(requirePermission('admin:roles'))` in `admin.ts`). This matches the PRD's Access Control table exactly ("Configure a Home pill's allow-list — Project Admin (existing `admin:roles` gate)"). **Risk if wrong:** none — explicit in the PRD.
- **Allow-list picker is edit-only-after-add, not part of the initial Add forms**: `SkillPillAddForm`/`McpPillAddForm` (`AdminProjectSettings.tsx`) deliberately keep pill creation minimal (label, skill/server name, model, effort) — richer per-pill fields like `description` and `bypassScopePolicy` are only editable in the rendered pill list afterward (`pillList` / `pillItem` rows). The allow-list picker follows this same precedent: it appears on each existing pill row, not in the quick-add form. Derived from the PRD's own wording ("gains a user/group selection control on each pill row... so an admin sets or clears an allow-list without leaving the pill editor") and the existing `description`/`bypassScopePolicy` placement. **Risk if wrong:** low — an admin can still add the pill first and immediately configure its allow-list in the same edit session before saving.
- **Reuse `GroupAwarePeoplePicker` and the existing `groupsWithMembers`/`allUsers` state, not a new component**: This is the exact component `renderApproverSection` already binds to `selectedUserIds`/`selectedGroupIds` for design-doc, PRD, prototype, test-case, and ADR reviewer pools. The PRD explicitly calls out "following the same picker pattern already used to build reviewer and approver pools." **Risk if wrong:** none — explicit in the PRD.
- **Field shape mirrors the `effort` precedent**: `allowedUserIds?: string[] | null` and `allowedGroupIds?: string[] | null` (optional + nullable, empty/omitted array means "everyone," per BR-001), matching `effort?: EffortLevel | null` on the same interfaces. **Risk if wrong:** none — consistent with every other optional pill field in `projectSettings.ts`.
- **No new cap or format constraint on allow-list size**: The PRD's own NFRs state "each pill's allow-lists are expected to hold a handful of user or group identifiers" with no volume requirement, and no existing approver/reviewer pool enforces a size cap. **Risk if wrong:** none — no DoD or NFR requires one.
- **Stale/removed picker entries are not proactively pruned on save**: If a previously allow-listed user or group is later removed from the project's available list, `GroupAwarePeoplePicker` already silently omits it from chip rendering (existing behavior shared by every reviewer/approver pool using this component today). This Feature introduces no new indicator for "N hidden entries" — building one exclusively for pills would be inconsistent with the unmodified reviewer-pool experience and is not required by any TBI Definition of Done. **Risk if wrong:** low — matches existing product behavior exactly; FEAT-002's resolver evaluates group membership live, so a stale reference simply grants no access rather than erroring (per the PRD's own group-membership assumption).
