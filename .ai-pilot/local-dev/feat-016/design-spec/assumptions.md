## Unresolved Items

Items that could not be inferred from the PRD, backlog, or codebase. Each must be decided before the relevant implementation step starts.

- ⚠ **Immutable project references**: The PRD says Skills "point to immutable project references" and that the five-role set follows the accepted ADR "Build from prompt (single-prompt-build-orchestration)". The ADR text was not in the repository checkout, so the meaning of "immutable" is unconfirmed. The tech spec assumes a repository-relative path to a committed file, checked by the documentation validation script. A commit SHA pin is the alternative. This decision blocks S2 to S6 (what each reference line in a Skill looks like) and VT-03 (what the path check proves). Confirm against the ADR: repository-relative committed paths (recommended, because a SHA pin breaks when Platform Engineering moves the template into a new repository), or SHA-pinned references.
- ⚠ **Feature dependencies**: FEAT-016 declares `dependsOn` FEAT-012 and FEAT-015 only. Its work items also need FEAT-014 (agent entry point, agent index, module maps, documentation validation script, design-system reference, component catalog) and FEAT-017 (handoff document with the ownership table and unresolved-decision register). TBI-037 to TBI-041 each require a link from the agent entry point and the agent index. TBI-041 and PBI-038 require the handoff document. PBI-036 needs the ownership table and the register to exclude Platform Engineering work and flag the open RBAC decision. Without these edges, the Dev Workbench wave order can schedule FEAT-016 before the files it links to exist, and VT-02, VT-03, and the PBI-036 and PBI-038 dry runs cannot pass. Decide whether to add FEAT-014 and FEAT-017 to `dependsOn` (recommended), or to accept that S7 and the dry runs wait until both Features land in the template.
- ⚠ **Skill structure enforcement**: Every Skill must state inputs, outputs, and stop conditions, link from the entry point and index, and name only gates and paths that exist. Only the FEAT-014 documentation validation script (TBI-034) can enforce this without new tooling, and TBI-034 is outside this Feature. Decide whether TBI-034 gains a declarative rule block for role Skills (recommended; S8 adds the rules and covers VT-01 to VT-04), or whether these four checks stay review-only. A review-only outcome downgrades VT-01 to VT-04 from automated to manual.

## Assumptions Accepted

Inferences made during synthesis that were treated as resolved. Confirm these with stakeholders before implementation locks.

- **Skills root**: The five Skills live at `templates/full-stack-express/.agents/skills/<name>/SKILL.md`, in the same root as `api-contract` and `ui-standards`. FEAT-015 ships first, so its root wins. If FEAT-015 chose `.cursor/skills`, this Feature follows it. Derived from `foundation-skills/README.md` (harness-neutral root `.agents/skills`, legacy root `.cursor/skills`). Risk: two roots in one template. The agent entry point links every Skill explicitly, so discovery does not depend on the harness.
- **Skill names**: The directories are `planner`, `ui`, `developer`, `qa`, and `integration`, matching the PRD wording ("the planner skill", "the UI skill", and so on). Risk: `ui` reads close to `ui-standards`; each description states the difference.
- **Uniform Skill structure**: Each `SKILL.md` has frontmatter with `name` (equal to the directory name) and `description`, then the headings Purpose, Inputs, Procedure, Outputs, Stop conditions, and Boundaries. Derived from the Agent Skills contract enforced by `npx @apex/skills validate` and from the Apex Skill layout in `.cursor/skills/dev-orchestrator/SKILL.md`. Risk: a rubric of required headings in TBI-034 that differs from this list.
- **Report shapes live in the producing Skill**: The planner defines the plan layout, and QA defines the evidence report layout. The developer Skill consumes the plan; the integration Skill consumes the evidence report. No shared format document is added. Derived from the TBI dependency chain (TBI-037 before TBI-039; TBI-040 before TBI-041). Risk: a consumer drifts from a producer; VT-03 catches a broken link, and the rule-trace review (VT-08, VT-09) catches a mismatched layout.
- **Planner reads the handoff document**: TBI-037 lists four inputs (entry point, module maps, quality manifest, NFR manifest). The planner also reads the handoff document's ownership table and decision register, because PBI-036 scenarios (d) and (d2) cannot pass without them. Risk: the backlog authors intended the entry point to carry these facts; if so, the planner reads them there and the handoff reference is dropped.
- **Gate identifiers come from the quality manifest**: The twelve gates are build, type-check, lint, formatting, OpenAPI drift, migration validation, unit, component, API, integration, accessibility, and container build (TBI-027). The Skills name gates by manifest identifier and never hard-code script names. The manifest is authoritative. Documentation validation is not one of the twelve gates. Risk: a manifest rename breaks a Skill; VT-04 catches it.
- **Verification script names are provisional**: This spec writes `pnpm run docs:validate` and `pnpm run manifest:validate` as working names. TBI-005 owns the real script surface and TBI-029 and TBI-034 own the validators. The Skills themselves do not name them (see the previous item). Risk: the verification lines in the tech spec need a rename after TBI-005 lands.
- **Illustrative NFR values are detectable**: TBI-028 requires example values to carry an illustrative label in the NFR manifest schema. The planner (PBI-036 scenario c) and QA read that label. Risk: the label has a different shape; the Skill text then names the real field.
- **Development adapter detection**: The integration Skill (PBI-038 scenario d) reads the authentication mode and environment from the production environment settings named in the example environment file (TBI-004) and reports "not ready" when mode `development` is set with production. Derived from BR-002. The variable name is not in the PRD; S1 resolves it against the live template. Risk: no production settings file exists in the template; the Skill then reads the container definition's environment block.
- **QA may not be able to run every gate**: TBI-040 says "runs or reviews". When a gate cannot run in the agent's environment (for example, a container build without a container runtime), QA reports the gate as "not verified (not run)", never as passed. Derived from TBI-040's NFR (deferred gates are not verified). Risk: a reader treats "not run" as lower severity than "deferred"; both block a "verified" verdict.
- **Open decisions listing**: The integration Skill lists every entry in the handoff document's decision register with its extension point, and marks those whose extension point the build touches. Derived from PBI-038 scenario (c). Risk: a long list hides the relevant entries; the marking keeps them first.
- **Status vocabularies**: QA uses `passed`, `failed`, `not verified`, and `manifest error`. Integration uses `ready` and `not ready`. Derived from PBI-037 and PBI-038 acceptance criteria. Risk: a different vocabulary in the quality manifest summary; the QA Skill then maps to it.
- **TBI chain is a hard order**: TBI-039 after TBI-037, TBI-040 after TBI-039, TBI-041 after TBI-040, as declared. TBI-038 has no dependency. Dev Workbench treats item `dependsOn` as a completion constraint, so the tech spec does not relax the QA-after-developer edge even though the files do not overlap. Risk: slower delivery than a parallel plan.
- **Derived acceptance criteria**: The backlog gives four criteria per PBI, but not always one per scenario type. The design doc adds a derived row where a type is missing: PBI-035 (d) from its security NFR; PBI-036 (b) from the TBI-037 NFR; PBI-039 (d) from its accessibility NFR. They are marked "derived". Risk: reviewers read a derived row as a new requirement; the PBI owner can strike it.
- **"Approved Skills" means reviewed in a pull request**: The Feature description says "approved skills". No approval workflow is in scope. Platform Admin approves through normal review of the template. Risk: a recorded sign-off is wanted; that is an extra process outside this Feature.
- **Behavior is verified by reviewer dry runs, not CI**: The generated application has no AI runtime (PRD), so no deterministic test can run a Skill. Behavior VTs are manual dry runs against scratch copies of the manifests (never committed) with the transcript excerpt recorded in the pull request. Structure and references are checked statically. Risk: dry-run outcomes vary between agent models; the rule-trace review (VT-06 to VT-10) fixes each criterion to a quoted normative sentence.
- **Target surface label**: The PRD labels the template `Full-stack (both client and server)`. This Feature ships only Markdown and writes no client or server code. The design doc keeps the PRD label and states the real deliverable in the experience notes. Risk: a reader expects code; the ownership answers say "No" for all five layers.
- **Apex stays untouched**: No file under `src/`, `migrations/`, `.cursor/`, or any Apex config changes. Skill Markdown must pass Apex's root `prettier --check .` using the existing `.prettierrc`; no ignore entry is added, because `.cursor/rules/scope-discipline.mdc` bars config edits without permission. The PRD-level question on an ignore entry (TBI-001) stays open and does not block this Feature. Risk: Prettier rewrites table alignment; authors run `npx prettier --write` on the Skill directory before commit.
- **Persona mapping**: Platform Engineering maps to `Platform Admin`; a QA agent acts for `QA`; the UI specialist agent acts for `UI/UX`; the development and planner agents act for `Developer`. Derived from the PRD assumptions. Risk: none beyond the PRD's own.
- **Feature Flag**: None. The PRD says "Flag required: No", and the Skills do not change Apex runtime behavior. The template's own flag interface (FEAT-008) is unrelated.
