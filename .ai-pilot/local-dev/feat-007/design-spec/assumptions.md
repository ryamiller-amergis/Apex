# Assumptions & Unresolved Items — Observability and Graceful Shutdown

> **PRD slug:** `full-stack-express-starter-template` | **Priority:** Must Have | **Feature flag:** `None`
> Shared between [design-doc-design.md](design-doc-design.md) and [design-doc-tech-spec.md](design-doc-tech-spec.md).
> Resolve all ⚠ items before implementation begins.

---

## Unresolved Items

Items that could not be inferred from the PRD, backlog, or codebase. Each must be decided before the relevant implementation step starts.

- ⚠ **Readiness response while the listener refuses connections**: PBI-015 (d) says that during shutdown "readiness reports not ready and new connections are not accepted". TBI-018 also says new connections are refused after the signal. Once the listener closes, a probe on a new connection gets a refusal, not a not-ready response. Only a keep-alive connection opened before the signal can receive the not-ready body. The spec flips readiness first, closes the listener in the same tick, and adds no delay (S7, VT-25). The alternative is an optional `SHUTDOWN_DRAIN_DELAY_MS` (default 0) between the readiness flip and the listener close, so probes see "not ready" before they see refusals. The PRD puts load balancer deregistration out of scope, so the default stays at no delay. The team must confirm no delay, or approve the optional variable.
- ⚠ **Exit status after a forced shutdown**: PBI-015 (a) requires exit status zero on a clean drain. PBI-015 (b) says the process "exits and logs which work was abandoned" without naming a status. The spec uses exit status `1` when it abandons requests, so an orchestrator can tell a forced stop from a clean one (S7, VT-18, VT-23). Apex's own drain in `src/server/services/interactiveActorHost/shutdownDrain` exits `0` at the deadline. The team must confirm `1`, or choose `0` and rely on the log line alone.
- ⚠ **Source of the database-call metric**: TBI-017 requires metrics for database calls. The spec assumes the pinned `@opentelemetry/instrumentation-pg` emits a client operation duration histogram. Older releases emit spans only. S5 checks the pinned version first. If it emits no metric, S5 records a `db.client.operation.duration` histogram inside the data-access module's pool wrapper. The team must accept that fallback, which adds a metrics call to the data-access module (FEAT-003), or restrict TBI-017 to database spans.
- ⚠ **Module format and instrumentation loading**: The PRD and backlog do not say whether the API builds to ESM or CommonJS. OpenTelemetry auto-instrumentation must load before `http`, `express`, and `pg`. The spec assumes `node --import ./dist/instrument.js dist/main.js`, which works for both formats. The owners of TBI-001 (workspace), TBI-014 (composition root), and the container definition in FEAT-013 must agree on the format and use the same start command. A wrapper such as `pnpm start` as the container command also breaks signal delivery (see the PID 1 assumption below). Decision needed before S4.

## Assumptions Accepted

Inferences made during synthesis that were treated as resolved. Confirm these with stakeholders before implementation locks.

- **Template layout and paths**: The spec places API code under `templates/full-stack-express/apps/api/src/` and shared config under `packages/config`. `templates/` is empty at the pinned SHA, and TBI-001 owns the final layout. If TBI-001 picks other folder names, only the paths in this spec change.
- **Apex code stays untouched**: All work lands in `templates/full-stack-express/`. The Apex-only rules (`rbac-governance.mdc`, `scope-discipline.mdc`, `src/server/index.ts` patterns) apply to Apex code and not here. Derived from PRD "Isolation and delivery" and BR-008. Risk: none unless a task edits Apex root files.
- **Missing backlog dependency on FEAT-002**: FEAT-007 lists only FEAT-001 as a dependency. TBI-016 and TBI-017 need the typed environment module from TBI-004 (FEAT-002) to read `LOG_LEVEL` and the telemetry settings. The plan treats TBI-004 as a prerequisite of S1. Risk: a team that builds FEAT-007 first would write a second, unvalidated config reader.
- **Seam between FEAT-007 and FEAT-006**: FEAT-006 depends on FEAT-007, but TBI-014 (composition root) wires the pieces together. FEAT-007 ships and tests the request ID middleware, the request and error logging middleware, `instrument.ts`, and the shutdown controller. TBI-014 mounts them and calls `app.listen`. PBI-015 (d) needs the real `/health/ready` handler from PBI-012, so VT-25 tests a fixture probe route and VT-26 runs against the real endpoint after FEAT-006 lands.
- **Request ID rules**: Header name `X-Request-Id` (declared on every route by TBI-011). A caller value is reused when it matches `^[A-Za-z0-9._-]{1,64}$`. Any other value is replaced with `crypto.randomUUID()`. The PRD says "over-long or malformed" without defining either. Risk: a caller can send a value that equals a real subject. The caller already knows that value, so the log learns nothing new.
- **Correlation ID**: The PRD names request and correlation IDs. The spec defines the correlation ID as a valid inbound `X-Correlation-Id` header, or the request ID when the header is absent or invalid. It appears in logs only and is not a response header, because the contracts package declares only the request ID header. Logs also carry `trace_id` and `span_id` from the active OpenTelemetry span.
- **`close()` on the data-access interface**: TBI-006 lists find, create, and update. TBI-018 needs the database pool closed, and the data-access module must be the only importer of the Drizzle client (TBI-006 NFR). The spec adds `close(): Promise<void>` to that interface. Apex's `postgresql-db.mdc` takes the same position for its own pool. Risk: the FEAT-003 owner must accept the interface change.
- **PostgreSQL driver is `pg` (node-postgres)**: Drizzle supports several drivers, and TBI-006 only says "PostgreSQL driver". `@opentelemetry/instrumentation-pg` covers `pg` only. A different driver needs a different instrumentation package and changes S5.
- **OTLP over HTTP only**: The spec supports `OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf` and no gRPC. ADOT and CloudWatch collectors accept OTLP/HTTP, so the choice meets PBI-014 and keeps dependencies small. Exporter names `otlp`, `console`, and `none` are valid for `OTEL_TRACES_EXPORTER` and `OTEL_METRICS_EXPORTER`. Risk: a platform that requires gRPC needs a collector in front.
- **Telemetry enablement rule**: The SDK starts only when `OTEL_SDK_DISABLED` is not `true` and an OTLP endpoint (`OTEL_EXPORTER_OTLP_ENDPOINT`, or a signal-specific endpoint) is set, or an exporter is set to `console`. Otherwise the application never constructs the SDK, and the OpenTelemetry API stays a no-op. The PRD only says "disabled cleanly when no exporter is configured".
- **Shutdown time limit**: `SHUTDOWN_TIMEOUT_MS`, default `25000`, accepted range `1000`–`120000`. The default sits below the 30-second default container stop timeout common to orchestrators, and the platform sets the real stop timeout (out of scope per PBI-015). The drain phase gets the limit minus a cleanup budget of `min(5000, 20% of the limit)`. Database close and telemetry flush share the rest. Risk: if the platform stop timeout is shorter than the limit, the platform kills the process first.
- **Signals handled**: `SIGTERM` and `SIGINT`. The first starts shutdown. A second signal during shutdown ends the drain at once, runs the bounded cleanup, and exits with status `1`. No HTTP endpoint triggers shutdown. Process-level fatal handlers (`uncaughtException`, `unhandledRejection`) are not part of this feature, and Node's default behavior stays.
- **Requests that arrive during the drain**: Requests on connections that were open before the signal run to completion and get `Connection: close`. The spec does not answer them with 503. This follows PBI-015 (a) ("dropping requests") and BR-005 (responses follow the contract).
- **Redaction approach**: Pino key-based `redact` for the names `displayName`, `display_name`, `email`, `externalSubject`, `external_subject`, `subject`, and `sub` at depths 0–3, plus allowlist serializers for request, response, and error objects, plus a rule that nothing logs request bodies, headers, or query strings. The error serializer keeps `type`, `code`, `message`, and `stack`, and drops PostgreSQL `detail`, `where`, `parameters`, and query text, because `detail` carries the offending value. A value-level scanner of every log line was rejected: it adds string scanning to the request path and cannot catch values that are not in the request context. Risk: a developer who interpolates an identity value into a message string defeats key-based redaction. The marker-value tests (VT-08) and the module docs guard this.
- **Health request log level**: Requests to `/health/live` and `/health/ready` log at `debug`, so probe traffic does not fill logs at `info`. The request ID rule still holds for them.
- **Exporter settings are never logged**: Startup logs report only whether telemetry is enabled and which exporters run. The endpoint, headers, and any URL user information are never logged, because `OTEL_EXPORTER_OTLP_HEADERS` can carry credentials (PBI-014 NFR). Config validation errors name the variable and never print its value.
- **Export failure logging is rate-limited**: The OpenTelemetry diagnostic logger routes to Pino at `warn`. The adapter logs the same message at most once per 60 seconds, so an unreachable collector does not flood logs.
- **Log destination**: Pino writes to stdout through an asynchronous destination (no blocking work on the request path). Shutdown flushes the logger before exit. Pretty printing is a developer-side pipe (`pino-pretty`) and never part of application code, because the DoD requires single-line JSON.
- **Container starts `node` directly**: Shutdown only works if the process receives `SIGTERM`. The production container (FEAT-013, BR-014) must run `node` as the main process and not through `pnpm` or a shell wrapper. This spec does not edit FEAT-013 but lists the requirement in its rollback and deployment section.
- **Process-level tests run on POSIX only**: VT-22 to VT-25 send real signals to a child process and run on Linux and macOS. Windows developers run them in a container or WSL.
- **Persona mapping**: Platform Engineering maps to `Platform Admin` and template consumers map to `Developer`, as the PRD assumptions state. Neither persona has an application-level permission in the template (BR-003).
