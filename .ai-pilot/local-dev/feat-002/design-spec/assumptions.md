# Assumptions & Unresolved Items — Shared Cursor-like Slide-out Chat

> **PRD slug:** `status-driven-agent-home` | **Priority:** Must Have | **Feature flag:** `None` (ships behind the existing `agent-home` flag, unchanged)
> Shared between [design-doc-design.md](design-doc-design.md) and [design-doc-tech-spec.md](design-doc-tech-spec.md).
> Resolve all ⚠ items before implementation begins.

---

## Unresolved Items

- ⚠ **Two competing thread identities on Home**: `AgentHome.tsx` tracks its own chat thread today via a per-project `sessionStorage` key (`agentHomeThreadId:{project}`) and a `?thread=` URL param, completely independent of the App-level `activeThreadId` state that already drives `ChatAgentPanel` everywhere else (`src/client/App.tsx`). Once Home's inline compose UI is replaced by the shared slide-out, exactly one of these must become the single source of truth. This blocks TBI-006 and PBI-006's "resume where I left off" requirement — implementation must decide whether the App-level `activeThreadId` absorbs the last `agentHomeThreadId:{project}` value on first load post-rollout, or whether users simply start a fresh thread the first time they open the new toggle.
- ⚠ **Inline "Recent Threads" preview vs. the existing full-history toggle**: The approved prototype shows a short inline "Recent Threads" list with a "See all" link sitting directly above the transcript. `ChatAgentPanel.tsx` already ships a different pattern today — a `⏱ History` header button (`chat-agent-history-btn`) that swaps the entire panel body for `ThreadHistorySidebar`. TBI-006/TBI-007 do not say which one wins. This blocks the shell's `topSlot` content contract — implementation must decide whether the prototype's inline preview list is built as new UI, or whether the existing toggle-to-sidebar pattern is kept as-is and the prototype's list is treated as illustrative only.
- ⚠ **Scope of the ported skill pills / MCP pills**: `quickSkillPills`/`quickMcpPills` (from `useProjectSkillConfig`) exist today only inside `AgentHome.tsx`'s full-page compose view. TBI-006 asks to move them "into the slide-out," but `ChatAgentPanel` is also opened from every non-Home page via `AppHeader`'s existing opener. This blocks the shell's empty-state design — implementation must decide whether pills render whenever `ChatAgentPanel` starts a new thread from *any* page, or only when the panel was opened via Home's right-edge toggle.
- ⚠ **Calendar Work-Item Assistant's drag/minimize interaction**: `CalendarWorkItemAssistantPanel.tsx` currently supports free-floating drag-to-reposition (`pos`, `isMoving`) and a minimize control (`minimized`) that no other panel has. PBI-007 requires all four panels to "present the same frame," which the shared shell's fixed right-edge position does not preserve. This blocks TBI-007/S9 — implementation must confirm whether this is an accepted, intentional feature removal for Calendar users, or whether the shell needs an opt-in "floating mode" for this one consumer.
- ⚠ **`data-testid` stability across the shell extraction**: Each of the four panels has its own existing `data-testid` values (`chat-agent-*`, `prd-assistant-*`, `calendar-assistant-*`, and Design Doc's equivalents) referenced by existing tests. This blocks the refactor sequencing in TBI-007 — implementation must confirm whether the shared shell is required to preserve every existing id unchanged (safest, assumed default below) or whether a consolidated new naming scheme is acceptable, which would require updating every existing test that references the old ids.
- ⚠ **Fate of the `'closed'` `ChatThreadStatus` value**: `ChatThreadStatus` (`src/shared/types/chat.ts`) includes a `'closed'` state distinct from `'idle' | 'running' | 'error'`, and `ChatAgentPanel`'s status bar already renders a `statusDotClosed` / "Thread closed" label for it. Once Close stops calling `closeThread.mutateAsync` (TBI-008), it is unclear whether any other event still produces this status, or whether the status bar's `'closed'` branch and copy become dead code. This blocks TBI-008/S3 — implementation must confirm whether `'closed'` remains a reachable thread state after this change.

## Assumptions Accepted

- **Feature 2's surface is frontend-only, not full-stack**: The PRD's epic-level `## Target Surface` states "Full-stack (both client and server)," but that reflects Feature 1's (Pipeline Status Dashboard) server-side aggregation work. Every TBI/PBI under Feature 2 (`FEAT-002`) lists `technicalDependencies` pointing only at "the existing chat-panel component and its underlying chat session hook" — no route, service, or schema dependency. Derived from the backlog JSON's per-item `technicalDependencies` arrays. Risk if wrong: a hidden server requirement (e.g. a new "soft-close" endpoint) would be missed in planning.
- **`AgentSlideOutShell` is the correct name and location for the new deep module**: Placed in `src/client/components/agentChat/`, alongside the already-shared `AgentComposer.tsx`, `AgentTranscript.tsx`, `AgentMessage.tsx`, and `AgentTypingIndicator.tsx`. Derived from that folder's existing convention of holding cross-panel chat primitives, and from `AgentTranscript.tsx` already existing there, fully built, but unused by any of the four panels today. Risk if wrong: the shell could just as reasonably live directly in `src/client/components/` as a sibling of `ChatAgentPanel.tsx`; low risk either way since it is a pure move.
- **No new RBAC permission key is needed**: The shell reuses `chat:view` / `chat:create` (Home toggle) and each assistant's existing `prds:review` / `design-docs:review` / `calendar:view` gate exactly as documented in `.cursor/rules/rbac-governance.mdc` and the PRD's Access Control table. Derived from every PBI's `nonFunctionalRequirements.security` explicitly stating "no new permission is introduced." Risk if wrong: low — this is stated directly in the PRD, not inferred.
- **`useBreakpoint()`'s existing 768px mobile query is the correct "narrow viewport" trigger**: `src/client/hooks/useBreakpoint.ts` defines `MOBILE_QUERY = '(max-width: 768px)'`, exactly matching the breakpoint already hardcoded in `ChatAgentPanel.module.css`'s `@media (max-width: 768px)` rule. Derived from the two thresholds already being identical in the current codebase (not coincidental). Risk if wrong: a mismatched JS/CSS breakpoint would make `isMobile`-gated behavior (e.g. ARIA role changes) fire at a different width than the visual overlay switch.
- **The three document/work-item assistants' thread-provisioning endpoints are untouched**: `POST /api/interviews/prds/:id/assistant-thread`, `POST /api/interviews/design-docs/:id/assistant-thread`, and the Calendar assistant's session-creation endpoint keep their current request/response shapes; only the client-side chrome around them moves to the shared shell. Derived from TBI-007's description scoping the change to "one shared frame... while each assistant keeps its own additional actions," with no PBI/TBI mentioning those routes. Risk if wrong: low — no backlog item references changing them.

## Questions for Developer (sign-off needed)

Each item below corresponds to an `[impacts-existing]` line in `design-doc-tech-spec.md`'s **UI Changes (from approved prototype)** checklist. Confirm or defer each before implementation starts.

1. **Enable `chatOpen` on `/home`.** Today `App.tsx` force-closes the header chat panel and hides its opener button whenever `currentView === 'home'`. This change removes both guards so the shared slide-out can open over the new dashboard. **Go/no-go:** approve removing these two guards now, or defer until FEAT-001's dashboard has actually replaced Home's page body?
2. **Retire `AgentHome.tsx`'s inline compose view.** The logo, "What would you like to work on?" heading, input area, and pill row currently rendered as Home's page body are removed in favor of the FEAT-001 dashboard + slide-out. **Go/no-go:** confirm this removal ships in the same release as FEAT-001, not before (Home would otherwise have neither the old compose UI nor a working dashboard)?
3. **Port skill pills / MCP pills into `ChatAgentPanel`.** This adds a `useProjectSkillConfig`/`useSkillList` dependency to a component used from every page's header opener, not just Home. **Go/no-go:** approve pills appearing whenever the panel starts a fresh thread from *any* page, or restrict them to Home-launched sessions only (see the matching Unresolved Item above)?
4. **Reconcile inline "Recent Threads" vs. the existing `⏱ History` toggle.** **Go/no-go:** build the prototype's inline preview list as new UI, or keep the existing toggle-to-`ThreadHistorySidebar` pattern and treat the prototype's list as illustrative only?
5. **Replace `ChatAgentPanel`'s current empty state.** "No active chat" / single "Start free chat" button is replaced by "No conversation yet" plus three quick-start shortcuts. **Go/no-go:** approve replacing the existing empty-state copy and action, or keep the current single-button state and add shortcuts alongside it?
6. **Restyle the error/reconnecting state.** The panel's current `statusDotError` / "Error occurred" status-bar treatment is replaced by an "Unable to connect" message with a retry affordance in the transcript area. **Go/no-go:** approve consolidating these into one presentation, or keep both (status bar label *and* transcript-area message)?
7. **Apply the shared shell to all three document/work-item assistants, including dropping Calendar's drag/minimize.** **Go/no-go:** approve retiring `CalendarWorkItemAssistantPanel`'s free-floating drag-to-move and minimize control as part of adopting the fixed-position shared shell (see the matching Unresolved Item above)?
8. **Remove the destructive `closeThread.mutateAsync` call from `ChatAgentPanel.handleClose`.** This call currently issues `DELETE /api/chat/threads/:id` → `permanentlyDeleteThread`, i.e. today's Close button **permanently deletes** the thread from memory, the workspace, and Postgres. **Go/no-go:** confirm removing this call entirely (Close only hides the panel) is correct, and that no other caller relies on Close-as-delete behavior?

## Risk to Existing Functionality

The highest-severity regression risk in this Feature is **item 8 above**: `ChatAgentPanel`'s Close button currently performs a hard delete of the active thread (`DELETE /api/chat/threads/:id` → `permanentlyDeleteThread`), sharing the exact same mutation (`useCloseThread`) and endpoint as `ThreadHistorySidebar`'s explicit per-row "Delete thread" action (`useDeleteThread`). If the fix in TBI-008 is implemented incorrectly — for example, by only changing the client-side label/animation without removing the underlying mutation call — users will continue to silently lose chat history every time they close the panel, which is the exact defect this Feature exists to fix. Any test suite change for TBI-008 must assert the *absence* of a network call on Close, not just the presence of a "panel hidden" state.

Secondary risks: (a) porting skill/MCP pills into the globally-shared `ChatAgentPanel` (items 3–4) could regress the panel's behavior on non-Home pages if the new pill UI is not correctly scoped; (b) dropping Calendar's drag/minimize (item 7) is a visible feature loss for existing Calendar Work-Item Assistant users if not explicitly signed off; (c) replacing the panel's empty and error states (items 5–6) changes copy and layout that existing component/E2E tests may assert against literally, so those tests need updating alongside the change, not after.
