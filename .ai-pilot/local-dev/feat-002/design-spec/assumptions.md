# Assumptions & Unresolved Items — Enforce Home Pill Access

> **PRD slug:** `home-pill-access-control` | **Priority:** Must Have | **Feature flag:** `None`
> Shared between [design-doc-design.md](design-doc-design.md) and [design-doc-tech-spec.md](design-doc-tech-spec.md).
> Resolve all ⚠ items before implementation begins.

---

## Unresolved Items

- ⚠ **Client signal for "pills exist but I'm allowed on none"**: `GET /api/skill-config` (`src/server/routes/api.ts`) returns `quickSkillPills` and `quickMcpPills` as flat arrays with no separate indicator of whether the *project* has any configured pills at all. Today, `ChatAgentPanel.tsx`'s `hasHomePills = quickSkillPills.length > 0 || quickMcpPills.length > 0` is the only signal the composer has, and it is computed from the arrays the server already returns. Once TBI-004 filters those arrays to the caller's allowed subset, a caller allowed on zero of a project's configured pills receives the exact same `{ quickSkillPills: [], quickMcpPills: [] }` shape as a project with no pills configured at all — the two cases are indistinguishable from the response TBI-004's own non-functional requirement describes ("No new fields are added to the public response beyond the existing pill shape minus the two allow-list fields"). Without an additional signal, TBI-006 cannot implement its Definition of Done item "Composer disables pill-less send when the project has pills and the caller's filtered arrays are both empty" while also satisfying "Composer allows pill-less send unchanged when the project has no configured pills" — both branches read as the same empty-arrays state. This blocks whether TBI-004 may add any field to the response at all.
  **Recommended default (applied in this spec):** add exactly one new boolean field, `homePillsConfigured`, to the `GET /api/skill-config` response and to `ProjectSkillConfigResponse` (`src/shared/types/projectSettings.ts`). It reports only whether the *project* has at least one configured skill or MCP pill (skill/MCP counts already partially observable via the pre-filter unauthenticated pill lists on other surfaces) — it carries no user or group identifiers and does not depend on the caller, so it does not reopen the "never leak who is on an allow-list" requirement. Interpret TBI-004's "no new fields" NFR as "no new pill-identity or allow-list fields" rather than "no new fields of any kind," since the literal reading makes TBI-006 unimplementable as specified. Confirm this interpretation with the PRD owner before implementation; if rejected, the fallback is to have the client separately call the existing `GET /api/skill-configs` (admin-facing repo-list endpoint) — but that endpoint has no caller-filtering and does not solve the problem, so `homePillsConfigured` is the recommended path.

- ⚠ **Group-ID lookup helper does not yet exist**: The pill access resolver (TBI-003) needs the caller's *current group ID memberships* to test against a pill's `allowedGroupIds`. The only existing helper, `groupService.getUserGroupNames()` (`src/server/services/groupService.ts`), returns group **names**, not IDs, and reviewer/approver pools (the cited prior art) expand membership server-side by group ID via a direct join rather than through a reusable "get my group IDs" helper. This spec adds a new `getUserGroupIds(userId): Promise<string[]>` export to `groupService.ts` (mirroring the existing `getUserGroupNames` shape) as the least-invasive option, rather than duplicating the join in the resolver's caller or forcing the resolver itself to depend on Drizzle (which would violate TBI-003's "pure function, no direct HTTP or database coupling of its own" requirement). Flagging because this is a net-new exported function not called out in any TBI's `definitionOfDone` or `technicalDependencies`, even though `TBI-003` lists "Existing project group membership lookups" as a dependency — that dependency currently only satisfies the name-based lookup, not the ID-based one this feature needs. No functional risk if this default is wrong — worst case the helper is named or shaped slightly differently at implementation time.

## Assumptions Accepted

- **FEAT-001 ships first and lands the allow-list fields on the shared pill types**: `QuickSkillPill` and both `QuickMcpPill` variants (`src/shared/types/projectSettings.ts`) do not yet carry `allowedUserIds`/`allowedGroupIds` at the pinned SHA (`e61f44bb9a311b601902eb8db3c9f49b42b50f93`) — confirmed by reading the file directly. This is expected: the backlog's own `Feature.dependsOn` marks `FEAT-002` ("Enforce Home Pill Access," this spec) as depending on `FEAT-001` ("Configure Home Pill Allow-Lists"), which owns `TBI-001`/`TBI-002`. This spec assumes FEAT-001 has already added `allowedUserIds?: string[] | null` and `allowedGroupIds?: string[] | null` to both pill shapes, and that the admin project-settings read/write path (`src/server/routes/admin.ts`, `projectSettingsService.ts`) already persists them, by the time FEAT-002 implementation begins. Risk if wrong: every TBI in this spec that reads `pill.allowedUserIds`/`pill.allowedGroupIds` needs FEAT-001 merged first; the Implementation Plan's Lane 1 step is blocked until then.

- **Allow-list group references are group IDs, not group names**: `allowedGroupIds` is assumed to store `appGroups.id` values (the same identifier already used by `projectApproverGroups.groupId` and `SetApproversRequest.designDocApproverGroups`/`prdApproverGroups`), not group display names. Derived from the PRD's explicit call-out that this feature "Follows the existing pattern used for reviewer and approver pools, which store group references... rather than snapshotting membership when a pool is saved" — every existing reviewer/approver pool stores group IDs. Risk if wrong: the resolver's group-membership check would need to compare against `appGroups.name` instead of `appGroupMembers.groupId`, a one-line change in the new `getUserGroupIds` helper's caller.

- **A caller's "current group ID memberships" are evaluated without project scoping, matching existing approver-pool behavior**: `getApproverPool()` (`projectSettingsService.ts`) expands a stored `groupId` to its members via a direct join on `appGroupMembers`/`appUsers` with no project filter on the membership rows themselves (scoping comes from which group was referenced, not from re-checking project assignment at read time). This spec's resolver follows the same shape: it checks whether the caller is a member of the *specific* group IDs referenced by a pill's `allowedGroupIds`, with no additional per-project membership re-validation. Risk if wrong: none identified — pill configuration is already project-scoped by which `project_skill_settings` row it lives on, so an allow-listed group is inherently project-relevant by construction.

- **"Configured pill" match is by exact `skillPath` / `mcpServerName` string equality**: Per the PRD's own stated assumption, a kickoff's `skillPath` matches a configured skill pill only on exact equality against that pill's `skillPath`, and an MCP kickoff matches only when `kickoff.mcpPill.mcpServerName` exactly equals a configured MCP pill's `mcpServerName`. No normalization (case-folding, trimming, path resolution) is applied. Risk if wrong: a caller could construct a kickoff with a near-miss `skillPath` to bypass allow-list enforcement by falling through to the pill-less branch — mitigated because the pill-less branch is equally gated by `canStartPillessChat`, so a mismatched `skillPath` never grants more access than pill-less chat already would.

- **Platform Admin bypass is evaluated via the existing `isSuperAdminRequest()` utility, not a new RBAC permission**: `src/server/utils/superAdmin.ts` already exposes `isSuperAdminRequest(req)`, and `requirePermission`/`requireGroupMembership`/`requireProjectAccess` (`src/server/middleware/rbac.ts`) already short-circuit on it. The pill access resolver takes a plain `isSuperAdmin: boolean` in its caller-context input (resolved by the route from `isSuperAdminRequest(req)` before calling the resolver) rather than re-deriving admin status itself, keeping the resolver free of HTTP/session coupling per TBI-003's explicit requirement. Risk if wrong: none — this is the same bypass every other admin-gated route in the codebase already uses; a different mechanism would be inconsistent with the rest of the app, not incorrect for this feature specifically.

- **No new RBAC permission key is introduced**: Per the PRD's explicit Out-of-Scope line ("A new RBAC permission key — enforcement layers on the existing `home:view` and `chat:create` gates") and confirmed against the permission catalog in `.cursor/rules/rbac-governance.mdc`, pill-level enforcement is a data-scoping concern layered under the existing `chat:view`/`chat:create` gates on `src/server/routes/chat.ts`, not a new access-control gate. Risk if wrong: none — explicitly stated in the PRD.

- **The pill access resolver is a new, framework-agnostic module named `homePillAccessResolver.ts`**: Placed in `src/server/services/`, following the existing naming convention for pure resolver modules with no DB/HTTP coupling of their own (`agentEffortResolver.ts`, `groundingProfileResolver.ts`). Callers (the `GET /api/skill-config` route and the `POST /api/chat/threads` route) are responsible for loading the caller's group IDs and super-admin status and passing them in. Risk if wrong: cosmetic — a reviewer could prefer a different file name or a `Service.ts` suffix; the module boundary and pure-function contract would not change.
