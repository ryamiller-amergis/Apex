# Assumptions & Unresolved Items — Admin Per-Module Effort Defaults

> **PRD slug:** `per-module-agent-effort-defaults` | **Priority:** Must Have | **Feature flag:** `None`
> Shared between [design-doc-design.md](design-doc-design.md) and [design-doc-tech-spec.md](design-doc-tech-spec.md).
> Resolve all ⚠ items before implementation begins.

---

## Unresolved Items

- ⚠ **Read-endpoint parity scope**: `GET /api/skill-config` (`src/server/routes/api.ts`) already omits several existing `*Model` fields from its response object today — `defaultModel`, `developmentModel`, `standupModel`, `designDocAssistantModel`, `designPrototypeModel`, `prdAssistantModel`, `prdValidationModel`, `designDocValidationModel`, `calendarAssistantModel`, `loadTestGenerationModel`, `designModuleModel`, `designModuleScopingModel` are all missing from that handler's explicit field list, even though they exist on `ProjectSkillConfig`. TBI-004's Definition of Done requires the "skill-config read endpoint returns the effort fields," but it doesn't say whether this feature should (a) add only the 20 new `*Effort`/`defaultEffort` fields for full parity going forward, or (b) also backfill the pre-existing missing `*Model` fields while the handler is already being touched. This blocks how large the diff to `api.ts` should be. **Recommended default (applied in this spec): (a)** — add full `*Effort` parity for all 20 fields so FEAT-003/FEAT-004 always have a complete read surface, but leave the pre-existing `*Model` gap unrepaired to keep this feature's blast radius limited to effort. Confirm with the engineering owner of `api.ts` before implementation if a broader cleanup is preferred.
- ⚠ **Project-wide Default Effort placement**: The PRD says the admin UI gets "one additional control per module" with "no new settings screen," but is silent on where the project-wide fallback selector (`defaultEffort`, the effort analog of `defaultModel`) should sit relative to the existing "Default Model" field in `AdminProjectSettings.tsx`'s Repository & Defaults section. This is a discoverability/UX call, not a pure implementation detail. **Recommended default (applied in this spec):** co-locate `Default Effort` directly beside `Default Model` in the same field block (no new sub-heading), consistent with the "no new settings screen" instruction. Confirm with product/UX before implementation if a separate "Effort Defaults" grouping is preferred instead.

## Assumptions Accepted

- **FEAT-001 is a hard prerequisite and is already delivered**: This feature (FEAT-002 / "Admin Per-Module Effort Defaults") consumes the shared `AgentEffort` union and the 20 nullable `TEXT` columns (19 per-module + `defaultEffort`) on `project_skill_settings` that FEAT-001 / TBI-001 adds. FEAT-002 performs **zero DDL and zero new Drizzle schema columns** — it only extends TypeScript request/response shapes, service wiring, and UI. Derived from the backlog's explicit `FEAT-002.dependsOn: ["FEAT-001"]` and TBI-004's cross-feature dependency note. Risk if wrong: every downstream step in this spec (S1–S7) is blocked until FEAT-001 actually ships those columns.
- **Field naming convention**: Each new column/field is named `{stage}Effort`, mirroring the existing `{stage}Model` field 1:1 (e.g. `interviewModel` → `interviewEffort`), plus a project-wide `defaultEffort` mirroring `defaultModel`. Derived directly from TBI-001's description ("one nullable effort column per existing `*Model` stage... plus a project-wide default effort column"). This yields exactly 20 new fields: `interviewEffort`, `prdEffort`, `adrEffort`, `designDocEffort`, `designDocAssistantEffort`, `designPrototypeEffort`, `testCaseEffort`, `designDocValidationEffort`, `prdAssistantEffort`, `prdValidationEffort`, `developmentEffort`, `standupEffort`, `featureRequestEffort`, `technicalEffort`, `issueEffort`, `calendarAssistantEffort`, `loadTestGenerationEffort`, `designModuleEffort`, `designModuleScopingEffort`, `defaultEffort`.
- **Closed allow-list is exactly three values, not four**: `low` / `medium` / `high` are the only members of the `AgentEffort` union; `null` is a separate "unset/Inherit" state, not a fourth enum member. Derived from the PRD's Implementation Decisions: "A closed union of `low` / `medium` / `high` (plus null, meaning inherit)". Risk if wrong: validators and the UI's "Inherit" option would need a different sentinel.
- **No new RBAC permission key**: Writes reuse the existing `admin:roles` gate already applied at the router level in `src/server/routes/admin.ts` (`router.use(requirePermission('admin:roles'))`); reads reuse the existing unauthenticated-but-session-scoped pattern already used by `GET /api/skill-config`. Explicit in BR-001, BR-003, and TBI-004's non-functional requirement "No new RBAC permission key — reuses the existing `admin:roles` write gate."
- **Validation follows the `approvalMode` precedent, not the `model` precedent**: Unlike the `*Model` fields (free text, accepted from whatever `Cursor.models.list()` returns, with no server-side allow-list — see `src/server/services/modelsService.ts`), effort needs a closed-set 400-on-invalid check per BR-003. The nearest existing precedent in this codebase is `isApprovalMode()` / `validateApprovalModeRequest()` in `src/server/services/projectSettingsService.ts` / `src/server/routes/admin.ts`, which already validates a small fixed-string union on this exact route and returns an early 400. This feature adds an `isAgentEffort()` guard and a `validateEffortFields()` helper following that same shape, rather than reusing the model path.
- **UI control is a plain native `<select>` with an explicit "Inherit" option**: matches the existing Model-override `<select>` exactly (empty-string option value ⇒ `null` on save), rather than introducing a new control type (radio group, segmented control, etc.). Derived from PRD: "an effort selector with an explicit 'Inherit' option, saved through the same validate/save path as the model control."
- **Stage-card layout promotes from 2-column to 3-column, not a stacked second row**: `src/client/components/AdminProjectSettings.tsx`'s `PipelineStageCard` renders Skill + Model in a 2-column `styles.stageFieldGrid` today. Adding Effort extends this to a 3-column grid (Skill | Model | Effort) for any stage that declares an `effortKey`, keeping one field row per stage card instead of stacking Effort below. This is an implementation-level layout call within an already-agreed "extend the existing control" pattern, not a product decision, so it is resolved here rather than escalated.
- **Representative-module test coverage, not exhaustive per-field duplication**: Direct unit tests exercise `interviewEffort` (a representative per-module field) and `defaultEffort` (the project-wide field) for accept/reject/null-round-trip; the remaining 18 `*Effort` fields share the identical validator and the identical spread-through-`upsertSkillConfig` code path, so they are covered indirectly rather than duplicated field-by-field. This mirrors the PRD's own stated testing philosophy for the sibling kickoff-resolution feature ("kickoff/create paths for at least two representative modules... proves resolution... generalize beyond one caller instead of being special-cased") and the explicit instruction to "extend those same tests in parallel rather than create a new, separate test file per module."
