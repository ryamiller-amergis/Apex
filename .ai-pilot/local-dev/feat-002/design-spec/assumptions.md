## Unresolved Items

Items that could not be inferred from the PRD, backlog, or codebase. Each must be decided before the relevant implementation step starts. Each carries the default this spec used, so work can start if no one answers.

- ⚠ **Default grants: roles versus groups.** The PRD says `workflow-evaluation:view` and `workflow-evaluation:submit` are granted by default to "Product-Owner, BA, Manager, Developer". Those four names are Groups (`groupService.ts` `DEFAULTS`). RBAC permissions attach to Roles (`admin`, `member`, `viewer`, plus custom roles), and no table links a Group to a permission. This spec grants both keys to the `admin` and `member` roles (S2). A QA or UI/UX user holding the `member` role therefore also gets both keys, which contradicts the PRD assumption that QA "is not a default". *Impact:* decides the contents of the S2 migration and the catalog row in `rbac-governance.mdc`. *Decision needed:* (1) accept that every `member` gets the keys (recommended; matches the `admin, member` defaults of `notifications:view` and `prds:review`), or (2) add `requireGroupMembership('Product-Owner','BA','Manager','Developer')` to the reviewer guards, which adds a second gate and a second place to misconfigure.
- ⚠ **Pilot project names.** The PRD says the flag targets "the Apex (project) and named pilot projects", but names none. The S3 seed creates one `project` rule with value `Apex` and nothing else. *Impact:* pilot projects must be added by a Platform Admin in Platform Admin → Feature Flags before the Beta stage, and each name must match the project string exactly (`evaluateFlags` compares `rule.value === ctx.project`). *Decision needed:* the list of pilot project names and the date each goes on.
- ⚠ **Platform Admin hub and flag scope.** The PRD says the hub is hidden when the flag is off, and the flag is evaluated per project. The hub spans projects, so no single project applies. This spec uses two checks: the server hub route calls `isFeatureOperational` (flag `enabled` and not archived, ignoring targeting rules), and the client hub tab uses `useFeatureFlag` for the project the Platform Admin has selected. *Impact:* a Platform Admin sitting in an untargeted project does not see the hub tab even though the server would answer. This is the one place where client and server checks can differ. *Decision needed:* confirm that mismatch is acceptable for the pilot, or ask for a project-free client flag read (a new endpoint, which this spec leaves out of scope).
- ⚠ **"Project from the session" has no server equivalent.** TBI-005's non-functional requirement says flag evaluation uses the project from the session, not the request body. Apex has no session project. `resolveRequestProject` in `src/server/middleware/rbac.ts` reads query, then route params, then body, then the `x-apex-project` header, and `requireProjectAccess` verifies the user is assigned to that project. This spec keeps that pattern and adds a guard that rejects any request whose body contains `project` (S4). *Impact:* without that guard, a caller could send a header for project B and `body.project` for project A, and the permission check would run against A while the flag and data scope run against B. *Decision needed:* confirm "session" means "the project resolved by `resolveRequestProject` after `requireProjectAccess`". If the PRD owner wants a true session-bound project, that is a platform change outside this Feature.

## Assumptions Accepted

Inferences made during synthesis that were treated as resolved. Confirm these with stakeholders before implementation locks.

- **No PBIs in this Feature.** FEAT-002 holds only TBI-004 and TBI-005. The design doc's four acceptance scenarios (happy, error, edge, negative) are written per TBI. *Derived from:* the backlog JSON. *Risk:* QA test-case generation that expects PBI rows will find none for this Feature.
- **Permission keys and category.** Keys are exactly `workflow-evaluation:view` and `workflow-evaluation:submit`, in a new category `workflow-evaluation`. *Derived from:* the PRD Access Control table and the "Add a Permission" workflow in `rbac-management`. *Risk:* none while categories stay free-text strings (the `playbooks`, `diagram` and `load-test` categories were added the same way).
- **Submit requires view.** Submit routes require both keys (`requirePermission` uses AND semantics). The form cannot render without reading definitions, which is a view operation. AdminRoles shows a warning when a role has submit without view, mirroring the existing `playbooks:author` without `playbooks:run` warning. *Risk:* a custom role granted only submit gets 403 on the form; the warning makes that visible at grant time.
- **Viewer role gets nothing.** The `viewer` role receives neither key. History carries lineage and job output quoting PRD text, which is more than read-only browsing. *Risk:* a PRD reviewer who holds only `viewer` cannot see feedback history.
- **Admin access reuses `admin:roles`.** "Anyone who can open Project Admin" maps to `requirePermission('admin:roles')`, the permission that gates `/admin/*` in the Modules table of `context.md`. Platform Admin maps to `requireSuperAdmin` and passes `requirePermission` through the existing super-admin bypass. No admin key is added, per the PRD and the Feature's out-of-scope list.
- **Super admins do not bypass the flag.** `requirePermission` lets super admins through, but the flag middleware runs after it and applies to everyone. This keeps the kill switch absolute. *Risk:* a Platform Admin cannot test the feature in an untargeted project without adding a `user` or `project` rule.
- **Refusal is 404.** An off flag returns `404 { error: 'Not found' }`, matching the `feature-flags` skill and the `work-board` gate in `apexWorkItems.ts`. A flag-evaluation error goes to `next(err)` (500) and the request does nothing else.
- **Order of guards.** Body-project rejection, then `requirePermission`, then `requireProjectAccess`, then the flag, as in `apexWorkItems.ts`. A user without the permission gets 403 even when the flag is off.
- **Flag seeding.** The flag is created by a migration with `enabled = true`, lifecycle `active`, and one `project` rule for `Apex`. `evaluateFlags` treats a flag with no rules as off, so an enabled flag with no rule is safe, but the DoD requires "targets the Apex project by default". Kill-switch changes go through the existing Platform Admin flag UI and audit log.
- **Cleanup plan.** Expected winner is `enabled`. Retire the flag after two stable sprints at full rollout, per `feature-flags.mdc` item 7.
- **Flag checks live only at route entry.** No flag check sits in the evaluation service, orchestrator or notifier. Create and retry are the only paths that start jobs or send alerts, and both run inside a request that already passed the gate. Worker result callbacks do not re-check the flag, so a run already in flight finishes and stores its result after a Platform Admin turns the flag off. *Risk:* if a later Feature adds a timer-driven enqueue, it must add its own flag read.
- **Shared constants file.** Permission keys go in a new `src/shared/types/workflowEvaluationAccess.ts`, not in the evaluation types file that FEAT-001's TBI-003 owns. This avoids a merge conflict between the two parallel groups. The flag key goes beside `WORK_BOARD_FLAG` in `src/shared/types/featureFlags.ts`.
- **Guard code in middleware, not inline.** `apexWorkItems.ts` inlines its flag check in the route file. The evaluation router, the admin routes, the export route and the hub all need the same check, so this spec puts it in `src/server/middleware/workflowEvaluationAccess.ts`. The `@feature-flag:` markers stay in that one file.
- **Client reads `can()` through `useAppShell`.** `PlaybookDashboardPage.tsx` takes `project` as a prop and calls `useAppShell()` and `useFeatureFlag(key, project)`. The new access hook does the same.
- **Flag cache window.** `useFeatureFlags` uses `staleTime: 60_000`. After a kill-switch change, the client can show the surface for up to 60 seconds. Server refusal is immediate; the client invalidates the flag query on the first 404 from an evaluation route.
- **Per-request flag cost.** `isFeatureEnabled` loads group ids and every non-archived flag with its rules on each call. At the stated low volume this is acceptable. Revisit if history polling or job-status polling in later Features multiplies calls.
- **Existing custom and project roles.** Project-specific roles override global roles (`getUserPermissions`). Users whose project role is custom do not receive the new keys from the migration. A Project Admin must grant them in Admin → Roles when the project joins the pilot. *Risk:* a pilot user sees no feedback surface and the cause is a missing grant, not the flag.
- **Migration timestamps.** The newest migration visible in the pinned checkout is `20261013120200_adr-thread-bundled-skill-flag.sql`. This spec uses `20261016120000` and `20261016120100`. *Risk:* if a newer file exists on the branch at implementation time, rename to sort after it.
- **Hub gate uses `isFeatureOperational`.** That helper already exists in `featureFlagService.ts`. See the third unresolved item for the client mismatch.
- **Hub rows for untargeted projects.** A hub row opens the per-project detail through the normal admin guard, which checks the flag for that project. If the flag is off for the project, the detail answers 404. The hub UI should show such rows as not openable. *Risk:* a Platform Admin clicks a row and sees an error if the hub Feature does not handle this.
