## Unresolved Items

Items that could not be inferred from the PRD, backlog, or codebase. Each must be decided before the relevant implementation step starts. The generation run was non-interactive, so each item carries the default the specs use. Change the default and the named step changes with it.

- ⚠ **Skills directory inside the template**: The PRD names five role skills plus `api-contract` and `ui-standards` (FEAT-015, FEAT-016) but gives no directory. The validator's `documents` glob, the agent index, and the `Skills` section of `AGENTS.md` all need that path. *Blocks:* S1 (config skeleton) and S2 (index entries). *Default used:* `.cursor/skills/<skill-name>/SKILL.md`, the layout Apex already uses and the layout Cursor-launched development agents load. *Decision needed:* FEAT-015 owner and Platform Engineering confirm the path. If it differs, edit one line in `docs/docs-check.config.json` and the `Skills` section.

- ⚠ **Does `docs:check` appear in the quality manifest?**: The PRD lists the manifest gates (build, type-check, lint, formatting, OpenAPI drift, migration validation, unit, component, API, integration, accessibility, container build). Documentation validation is not on that list, yet PBI-031 cites BR-013 ("gates are exposed as scripts; teams decide when they run"). FEAT-012 owns the manifest and its validator, and FEAT-014 does not depend on a change to either. *Blocks:* S5. *Default used:* add a `docs-validation` gate that runs `pnpm docs:check`, with no coverage floor and no tier. *Decision needed:* FEAT-012 owner confirms the gate entry fits the manifest schema. If rejected, `docs:check` stays a standalone script that the README and handoff document list.

- ⚠ **Enforcement of design-system reference and component catalog parity with `packages/ui`**: TBI-033's definition of done says both documents "match the UI package". TBI-034 lists four checks (links, sections, stale paths, index coverage) and none compares documents to package exports. A parity check has to read the package's public entry file, which breaks on `export *`. *Blocks:* the scope of S4. *Default used:* review-only. The stale-path check covers every file path the catalog names, and the PR checklist in `docs/component-catalog.md` asks the author to confirm each public export is listed. *Decision needed:* FEAT-009 owner and the team decide whether to add an export-name check once the UI package's entry file shape is fixed.

- ⚠ **Compatibility of template Markdown with Apex's root formatting check**: Inherited from the PRD ("conform to Apex's existing formatting rules, or approve a minimal ignore entry"). Apex's `.prettierrc` sets `semi`, `singleQuote`, `trailingComma: es5`, `printWidth: 80`, `tabWidth: 2`. The Apex pre-commit hook runs `lint-staged` only on `src/{client,server,shared}/**/*.{ts,tsx}` (root `README.md`) plus `check-data-testid.mjs` on `src/client` TSX, so neither reaches `templates/`. The command and glob of the root formatting check were not readable in the checkout. *Blocks:* S7. *Default used:* author every `.md`, `.json`, and `.mjs` file with Prettier using the Apex configuration, so the check passes without an ignore entry. *Decision needed:* TBI-001's owner confirms the approach for the whole template. This Feature follows that decision.

## Assumptions Accepted

Inferences made during synthesis that were treated as resolved. Confirm these with stakeholders before implementation locks.

- **Feature scope is documents plus one script**: The Feature ships Markdown files, one plain-text index, one JSON config, and one Node script with its tests, all under `templates/full-stack-express/`. It adds no HTTP endpoint, table, React component, Apex permission, or Apex file. *Derived from:* TBI-033, TBI-034, PBI-030, PBI-031, BR-008. *Risk if wrong:* none for Apex runtime; the owning-layer answers in the tech spec change.
- **Output file names `design-doc-*`**: The three output files use the `design-doc` prefix the generation request names, not the usual feature-slug prefix. Links between the files use those names. *Risk:* none; rename links if the app changes the convention.
- **Template layout paths**: Workspace members are `apps/web`, `apps/api`, `packages/contracts`, `packages/ui`, `packages/config`, matching the five members in TBI-001. The validator reads members from `pnpm-workspace.yaml`, so only the documentation examples depend on these names. *Risk if wrong:* the stale-path check reports the examples; fix the examples.
- **Entry-point file name `AGENTS.md`**: The PRD calls it "an agent entry-point document". `AGENTS.md` is the name Apex's own agents read first and the name Cursor and other agent tools look for. *Risk:* an agent runtime that expects a different name; the index and a README link cover it.
- **Index file `docs/agent-index.txt`**: One document per line, `<path>  <one-line summary>`, `#` starts a comment line. Plain text satisfies the PRD ("a plain-text index for agents") and the accessibility NFR. *Risk:* a consumer expecting a different convention such as `llms.txt`; the index can be copied to that name later.
- **Single module map file**: `docs/module-map.md` holds one heading per workspace member, not one file per module. TBI-033 says "each module has a map entry", which reads as an entry, not a file. One file gives the validator one place to look. *Risk:* large module sets make the file long; split later by adding a glob to the config.
- **The validator is a zero-dependency Node ESM script**: `scripts/check-docs.mjs`, no npm packages, runs before `pnpm install`. This follows `scripts/validate-foundation-skills.mjs` in Apex and keeps BR-009's pinned dependency set from growing. A Markdown-link-check library was rejected because it fetches external links by default, which PBI-031 forbids. *Risk:* the hand-written scanner supports ATX headings and inline links only; Setext headings and HTML anchors are ignored. The doc style guide in `AGENTS.md` states this.
- **Fragments are not validated**: `[text](file.md#section)` checks the file only. Azure DevOps Repos and GitHub generate different heading anchors, and the template targets Azure DevOps. *Risk:* a broken `#fragment` goes unreported.
- **What counts as a path in prose**: A stale-path candidate is an inline code span containing `/`, with a final segment that has a file extension (or a trailing `/`), whose first segment is an existing top-level entry of the template, or that starts with `./` or `../`. Fenced code blocks, glob patterns, placeholders (`{x}`, `<x>`), URLs, and paths matching `ignorePaths` are skipped. A line comment `<!-- docs-check-exempt -->` on the same or previous line skips a span, following the `data-testid-exempt` precedent in `scripts/check-data-testid.mjs`. *Risk:* a stale path whose first segment is not a top-level entry is missed.
- **Checks beyond TBI-034's four**: The validator also reports links that resolve outside the template root, case-mismatched links, documents not linked from `AGENTS.md`, missing required documents, module-map gaps, and Apex-specific terms outside the origin note. Each follows from an acceptance criterion or a business rule: PBI-030 (a), (c), and (d), BR-008, and the move to a separate Azure DevOps repository. *Risk:* extra findings on a later feature's documents; each rule has a config switch.
- **Links that leave the template root count as broken**: The template sits inside Apex today and becomes a repository root after bootstrap. A link such as `../../src/server/x.ts` resolves in Apex and breaks later. *Risk:* none worth carrying.
- **Case-sensitive link resolution**: The validator compares each path segment with the directory listing, so `Docs/Api.md` fails on macOS and Windows the same way it fails on Linux. *Risk:* none.
- **Origin note**: Apex-specific names (`Apex`, `Amergis`, `ai-pilot`, case-insensitive) may appear only under a heading named `Template origin`, until the next heading of equal or higher level. PBI-030 (d) says "an explicit note about the template's origin" and does not define the note's form. *Risk:* a stricter reviewer wants no mention at all; delete the section and the exemption.
- **Dependency order inside the Feature**: TBI-034 "depends on" TBI-033. The specs read that as "the validator needs the documented structure (S1)", not "the prose is finished". Validator development (S3, S4) starts after S1 and runs in parallel with content authoring (S2), and unit tests use fixture trees. S6 runs the validator on the real documents after both finish. *Risk if wrong:* the team wants strict serial order; serialize S2 before S3 at the cost of one lane.
- **Documents owned by other Features sit in this Feature's index**: The compatibility table (`docs/compatibility.md`) comes from TBI-002, skills from FEAT-015 and FEAT-016, and the handoff document from FEAT-017. This Feature owns the index and entry-point links and the config extension points (`documents`, `requiredDocuments`, `requiredSections`). Those Features append entries; they do not edit the script. *Risk:* a Feature adds a document and skips the index; `docs:check` reports it as `index-missing`.
- **Path of the committed OpenAPI document and the quality manifest**: `docs/api.md` and `docs/testing.md` link to files FEAT-004 and FEAT-012 produce. Their paths are not in the PRD, so the specs name them by role. The stale-path check reports any mismatch during S6. *Risk:* rework of two links.
- **Seeded ADR area**: `docs/adr/` holds a README index, a MADR-format template (the format Apex's ADR module generates), and records of decisions already in the PRD: Zod as contract authority (BR-004), no RBAC in the template (BR-003), forward-only production migrations (BR-006), and the docs-as-code knowledge base itself. The accepted Apex ADR "Build from prompt" is not copied, because its text was unavailable in the checkout and it is Apex content (BR-008). *Risk:* the team wants a different seed set.
- **Required headings per document kind**: Runbooks need `Purpose`, `Prerequisites`, `Steps`, `Verify`, `Troubleshooting`. ADR records need `Context and Problem Statement`, `Considered Options`, `Decision Outcome`. `AGENTS.md` needs `Start here`, `Documentation map`, `Skills`, `Scripts`. The PRD says "required sections" without listing them; these follow MADR and the document purposes. *Risk:* a team prefers other headings; edit the config, not the script.
- **Validator exit codes**: `0` clean, `1` one or more findings, `2` unusable configuration or invocation (missing config, missing entry point, unreadable root). Both non-zero codes print the problem. *Risk:* a pipeline that treats only `1` as a content failure; Platform Engineering reads the documented codes in the handoff.
- **Prose accuracy beyond the checks**: The validator proves links, headings, paths, and index coverage. It cannot prove that `docs/api.md` describes the endpoints correctly. Review and the contract and drift checks (FEAT-004) carry that. *Risk:* a stale statement with valid paths passes.
- **Secrets and identity values in documents**: PBI-030's security NFR (no secrets, real identity values, or internal host names) is met by authoring with synthetic values and by the supply-chain secret scan (FEAT-013). The validator does not scan for secrets. *Risk:* a leak caught only by the secret scan.
- **Unit tests for `scripts/` use a root Vitest project**: The shared test configuration from TBI-003 targets the web and API applications. FEAT-012's validators need the same root-level test setup, so this Feature reuses it and adds one only if FEAT-012 has not. *Risk:* two competing root configs; reconcile in review.
- **No feature flag, no telemetry, no schema change**: The PRD sets `Flag required: No`. The script is a command-line tool with no Pino or OpenTelemetry wiring. *Risk:* none.
