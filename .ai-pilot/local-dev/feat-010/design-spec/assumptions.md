## Unresolved Items

Items that could not be inferred from the PRD, backlog, or codebase. Each must be decided before the relevant implementation step starts.

- ⚠ **Sign-in action for the unauthenticated state**: PBI-019 says the user "is told I must sign in". The template defines no production identity provider and no sign-in route, so the screen has nothing to link to. The plan shows a message with no action (S2 builds this). The team must confirm a message-only state is acceptable, or name the extension point (a `signInUrl` setting in the web build-time environment, or a callback from the identity adapter) that a project fills in. Blocks S2 and VT-04, VT-11.
- ⚠ **Profile creation on first `GET /api/v1/me`**: The PRD asks Platform Engineering to confirm that the first authenticated `GET` creates the `app_users` row. The screen assumes it does, so a signed-in user always receives a profile and no screen-level empty or not-found state exists. If creation is not confirmed, `GET` can return 404 and the screen needs a "no profile yet" state. Blocks S3 and VT-01, VT-03.
- ⚠ **Display name and email length limits**: The backlog requires "maximum length" behavior (PBI-020 AC c) but states no numbers. The contracts package (TBI-009) must export the limits. This spec uses 100 characters for display name and 254 for email as working values. Tests import the limits from the contracts package and hard-code neither. Contracts owners must confirm or replace the values before S4.
- ⚠ **Wire format for a cleared email**: PBI-011 and PBI-020 say a cleared email is accepted, but the contract does not say how it travels. This spec assumes `PUT /api/v1/me` replaces the full representation and sends `email: null`. The alternative is to omit the key. Contracts owners must confirm the request schema before S4, and must confirm the plain-language validation messages (for example "Enter a display name") live in the shared Zod schema so the form reuses them.
- ⚠ **Route shape**: The backlog gives one route for this Feature, `/profile/details/edit`, and the PRD says the template has no Apex navigation entry. This spec adds a read route, `/profile`, and keeps `/profile/details/edit` for the form. If product wants one route that toggles between read and edit, S5 and VT-21 change. Confirm before S5.

## Assumptions Accepted

Inferences made during synthesis that were treated as resolved. Confirm these with stakeholders before implementation locks.

- **Frontend-only scope**: This Feature adds web client code only, including the web composition in TBI-022 (S1). The profile API (FEAT-006), contracts (FEAT-004), and UI package, shell, error boundary, and state components (FEAT-009) already exist when S1 starts. Derived from the Feature's `dependsOn` list and the phase plan, where Phase 4 follows Phase 3. Risk: if any dependency ships late, S1 is blocked; stub at the `fetch` boundary only as a stopgap.
- **Code protection**: The shell, navigation, header, and error boundary from FEAT-009 are used as they are. This Feature owns the route table, query client, and API client it creates in S1 and S5, and it adds an index route that redirects `/` to `/profile`. Derived from the existing-code protection rules in the kickoff context. Risk: if TBI-001 already placed an app entry file in `apps/web`, S1 edits that file instead of creating it.
- **Template layout names**: `templates/full-stack-express/apps/web`, `apps/api`, `packages/contracts`, `packages/ui`, `packages/config`, with package scope placeholder `@{scope}`. The backlog names the five members but not the folders; TBI-001 fixes them. Risk: low; rename paths in this spec if TBI-001 differs.
- **Contract and UI export names**: `getMe` and `updateMe` route definitions, `updateProfileRequestSchema`, `profileResponseSchema`, and UI package `LoadingState`, `ErrorState`, `EmptyState` are working names. TBI-009 and TBI-021 set the real names. Risk: names change; the file layout and behavior do not.
- **API client error shape**: This Feature builds the typed API client (TBI-022). It throws one `ApiError` that carries the HTTP status and the parsed Problem Details body, with an `isUnauthenticated` check. Derived from "Handle Problem Details errors and unauthenticated responses in one place". The client does not redirect on 401, because the sign-in destination is unresolved (see ⚠). Risk: if a project later adds a global redirect, the unauthenticated state moves to that handler and VT-04 changes.
- **Problem Details validation errors**: A 400 response carries a list of `{ field, message }` entries, one per invalid field (PBI-011 AC b: "naming each invalid field"). The form maps each entry to its input. Risk: a different list shape changes one mapper function.
- **Status display**: The `status` value comes from a Zod enum in the contracts package (the PRD leaves the set to implementation). The screen shows it as a text chip using a label map typed over that enum, so a new value fails type-checking until labeled. Color never carries the meaning alone.
- **No screen-level empty state**: Given create-on-first-access (see ⚠ above), the only empty state is an empty email, shown as "No email on file". PBI-021 AC c's "empty state" is this field-level state.
- **Form behavior**: The form uses React Hook Form with the shared Zod schema through `zodResolver`, `mode: 'onChange'` so over-limit input shows an error before submit (PBI-020 AC c). Inputs have no HTML `maxLength` attribute, because that would block the over-limit input the AC requires an error for. An empty email string converts to `null` through the shared schema's field, not a copied rule.
- **Cancel without confirmation**: Cancel returns to `/profile` and discards edits with no dialog. The form has two fields. Risk: product may want an unsaved-changes prompt; it would add one component and one VT.
- **Query behavior**: Query key `['profile', 'me']`, `retry: false` on the profile query so the error state appears at once and the user retries by choice, and no automatic retry on the mutation. After a successful save the cache is set from the response and then invalidated, so the read page shows the saved values at once and a background refetch confirms them. The boundary shows cached data when a background refetch fails, except on a 401, where it clears the cache and shows the sign-in state.
- **Success handoff**: After a save, the app navigates to `/profile` with router state `{ saved: true }`. The read page shows a `role="status"` message and moves focus to the page heading. Risk: router state survives a reload and could show the message again; accepted for a reference screen.
- **No client persistence or logging**: Profile values live only in the TanStack Query cache. The screen writes nothing to `localStorage`, `sessionStorage`, cookies, or the console. The PRD leaves data classification to Platform Engineering, so the screen takes the strictest handling by default.
- **No feature flag, no RBAC**: The PRD sets Flag required: No and defines no roles. The screen has no flag check and no permission check; the API's authenticated principal is the only gate. The template's own flag interface is not used here.
- **Standards source**: BR-015 requires the `ui-standards` skill (TBI-036), which Phase 6 authors after this screen exists. This spec applies Apex's `react-coding-standards.mdc` (functional components with typed props, hook order, TanStack Query in custom hooks, no fetching in effects, React Hook Form with Zod) and MUI theme tokens in place of Apex's CSS variables and CSS Modules in `ui-design-standards.mdc`, which belong to Apex's own client. PBI-034 reviews the finished screen against the skill. Risk: the skill differs and the screen needs follow-up edits.
- **Test selector convention**: `data-testid` values in kebab-case with a `profile-` prefix, following Apex's convention. TBI-021 defines the template's convention; rename if it differs.
- **Test harness**: Vitest and React Testing Library for component tests; Playwright with axe for journeys, theme runs, and state checks. The harness (TBI-023, TBI-025) comes from FEAT-011, a Phase 5 Feature. This Feature writes its tests with the same tools, and the VT rows that need the Playwright harness (VT-13, VT-16 to VT-19, VT-22) run once TBI-025 lands. State tests stub the network with Playwright `page.route`; VT-22 uses the real API and PostgreSQL.
- **Theme and shell controls**: The light/dark theme toggle and the shell navigation belong to FEAT-009. The profile screen only has to render legibly in both themes.
- **Error copy**: The screen shows fixed plain-language text for load and save failures. It never renders Problem Details `title`, `detail`, request IDs, or status codes outside field-level validation messages.
- **Document title**: Each profile route sets `document.title` ("Profile" and "Edit profile") for WCAG 2.4.2. A small effect in the page does this; React Router has no built-in setter.
- **Verification commands**: Script names `build`, `check`, and `test` at the template root follow TBI-005's named script surface. Adjust if TBI-005 names them differently. Template files must also pass Apex's root formatting check (TBI-001 NFR).
