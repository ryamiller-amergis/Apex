## Unresolved Items

Items that could not be inferred from the PRD, backlog, or codebase. Each must be decided before the relevant implementation step starts.

- ⚠ **OpenAPI tooling and Zod major version**: TBI-010 says the generation library comes from the organization-approved set, and the PRD names no tool. This blocks S3 and S4 in the tech spec. The design assumes the approved set includes Zod 4 (Apex's root `package.json` pins `zod ^4.3.6`). It converts schemas with Zod's built-in `z.toJSONSchema` (draft 2020-12, which OpenAPI 3.1 accepts as its schema dialect) and assembles `paths` and `components` in about 150 lines of our own code. It validates the committed file with one OpenAPI 3.1 validator package, and prints diffs with one diff package. **Decide:** (1) confirm the approved list allows Zod 4 and names one OpenAPI 3.1 validator and one diff library. (2) If the list pins Zod 3, replace the converter with an approved Zod-to-OpenAPI package and keep the rest of the design unchanged. Record the choice in the compatibility table (TBI-002).
- ⚠ **`app_users.status` value set**: The profile response schema in the contracts package must list the `status` values, and OpenAPI shows them as an enum. The PRD leaves the set to implementation (FEAT-003), and FEAT-004 does not depend on FEAT-003. This blocks the final shape of `getMe` and `putMe` (S2). **Recommended default:** `active` and `disabled`. **Decide:** confirm the set. The contracts package owns the literal list, because it cannot import the database layer. The data-access module (FEAT-003) must type-check that the database values are a subset of the list (`satisfies`), so the two cannot drift.
- ⚠ **Owner of the Express-side route inventory check**: PBI-006 scenario (d) requires the checks to report a handler that no contract defines. Finding handlers means reading the running Express app, and `apps/api` does not exist until FEAT-006 (Phase 3). The backlog assigns this to no TBI. This design ships the pure comparison (`compareRouteInventory`, S6) in FEAT-004. FEAT-006 would supply the Express adapter and the `routes:check` script (VT-18). **Decide:** confirm that FEAT-006 owns the adapter, and add it to TBI-014's definition of done. Until then, scenario (d) is only partly verifiable (VT-05 passes; VT-18 is blocked).
- ⚠ **`GET /api/v1/me` creates the profile on first access**: Inherited from the PRD ("Confirm this behavior"). The contract documents the behavior, so it fixes the status code (200 only, never 201) and the operation description. A `GET` with a write side effect also departs from HTTP safe-method semantics, which the `api-contract` skill (FEAT-013) will teach. **Decide:** confirm create-on-first-read, or add a different path to a profile (for example, `PUT /api/v1/me` as an upsert). The second option changes the contract and TBI-015.

## Assumptions Accepted

Inferences made during synthesis that were treated as resolved. Confirm these with stakeholders before implementation locks.

**Contract shape**

- **Validation failures return 400**: Malformed JSON and schema failures both return `400` with `application/problem+json`. The Problem Details `type` tells them apart (`urn:problem-type:malformed-body` and `urn:problem-type:validation-error`). Derived from PBI-006 (c), which says only "Problem Details validation error". Risk: teams that prefer `422` for schema failures must change one constant and regenerate.
- **Unknown request keys are rejected, not ignored**: Request body schemas use `z.strictObject`, so `PUT /api/v1/me` with `subject`, `id`, or `status` returns a validation error naming the field. OpenAPI shows `additionalProperties: false`. Derived from PBI-011 (d) and TBI-015, which both say "rejected or ignored as the contract defines". Rejecting is observable in tests and tells the caller the field has no effect. Response objects are strict too, so a handler that adds a field (for example the external subject) fails the conformance tests in FEAT-011 instead of leaking it. Risk: a client that sends extra keys breaks instead of being silently ignored.
- **Definition-time guard against user identifiers**: `defineRoute` throws at module load if a `params`, `query`, or `body` schema names a field in a fixed list (`userId`, `subject`, `sub`, `externalSubject`, `externalId`). This turns BR-001 and the TBI-015 requirement ("no route may accept a user identifier or subject") into a check that runs before any handler exists. A project that adds user administration with RBAC edits the list; the list is one constant. Risk: a legitimate field with one of these names needs the constant changed, which is a deliberate review point.
- **Profile response fields**: `displayName`, `email` (string or `null`), and `status`. The response omits the external identity subject, the internal UUID, and timestamps, because PBI-010 lists only display name, email, and status and BR-007 keeps identity values out of outputs we control. Risk: the web client (FEAT-010) may later want `updatedAt`; adding it is a backward-compatible change.
- **Profile field limits**: `displayName` is trimmed and holds 1 to 100 characters. `email` holds at most 254 characters and must be a valid address. `PUT /api/v1/me` replaces both editable fields, so an omitted or `null` email clears it. Derived from PBI-011 (b) and (c), which give no numbers. Risk: low; the numbers are constants in one file.
- **Problem Details members**: `type`, `title`, `status`, `detail` (optional), `instance` (optional), `requestId`, and `errors` (optional list of `{ pointer, code, message }`). The schema is strict, so an error body with a `stack` member does not match it. `errors[].message` comes from a fixed message catalog keyed by Zod issue code. It never echoes the submitted value, because BR-007 bans identity values in error bodies. Risk: callers lose Zod's richer default messages.
- **Problem `type` values are URNs**: `urn:problem-type:<name>` for `validation-error`, `malformed-body`, `authentication-required`, `not-found`, `rate-limited`, `not-ready`, and `internal-error`. The template has no domain to host type documents, and RFC 9457 allows any URI reference. Risk: a project that later publishes type documents replaces the prefix in one constant.
- **Readiness failure is a Problem Details body**: `GET /health/ready` returns `200 { status: "ready" }` or `503` with Problem Details (`not-ready`). PBI-012 asks for a "not-ready status", and BR-005 requires Problem Details for every error. Probes read the status code only. Risk: Platform Engineering expects a custom JSON body from the probe; the body carries no detail either way.
- **Standard responses are added by `defineRoute`**: Every route gets the `X-Request-Id` response header and a `500` Problem Details response. Routes with `auth: "principal"` also get `401` and `429`. Routes with any input also get `400`. The route author cannot override these with a non-Problem schema. `429` appears because FEAT-006 ships rate-limit hooks. Risk: the committed document lists a `429` that is off in a default environment.
- **Request ID header**: `X-Request-Id`, 1 to 128 characters from `[A-Za-z0-9._-]`. Whether the API honors an inbound value is a FEAT-006 and FEAT-007 decision; the contract fixes only the response header and format.
- **Pagination convention**: Cursor-based. Query `limit` (integer, default 20, maximum 100) and `cursor` (opaque string, at most 512 characters). Response `{ items, nextCursor }` with `nextCursor: null` on the last page. No reference endpoint uses it; a test-only route proves the helper. Risk: a project that needs jump-to-page must define offset pagination itself.
- **Path rules**: A route path is either `/api/v<n>/...` or `/health/...`. `defineRoute` throws at module load for anything else. Path parameters use Express syntax (`:thingId`); the generator writes `{thingId}` in OpenAPI. The `params` schema keys must match the path parameters exactly.
- **Security scheme is a placeholder**: Routes declare `auth: "principal"` or `"none"`. The document defines one scheme (`principal`, HTTP bearer) so operations carry a `security` entry. The PRD does not name the transport (the identity provider is an extension point), and the development adapter sends no credential. Risk: the production adapter uses a cookie or another transport; Platform Engineering changes one constant and regenerates.
- **Examples are optional and synthetic**: Profile routes carry one example each (`Ada Example`, `ada@example.test`). `.test` is a reserved top-level domain. A test scans the committed document and fails on any email outside reserved example domains.
- **Reference routes live in the contracts package**: `getHealthLive`, `getHealthReady`, `getMe`, and `putMe`. Health routes are included because the PRD requires a definition for every endpoint.

**Boundaries between work items and Features**

- **TBI-009 and TBI-011 split**: The backlog makes TBI-011 depend on TBI-009, yet TBI-009 needs error schemas. TBI-009 therefore ships the minimal `problemDetailsSchema` and request ID header. TBI-011 adds the problem type catalog, the Zod-issue mapper, the pagination helper, the path guard, and the conventions README.
- **Runtime consumers belong to other Features**: Express validation middleware and `registerRoute` (FEAT-006), the typed web client (FEAT-010), conformance tests (FEAT-011), the quality manifest entry for the drift gate (FEAT-012), and the `api-contract` skill (FEAT-013). This Feature exports what they need and nothing more.
- **Vitest runs in the contracts package from TBI-009 onward**: TBI-009 requires unit tests before FEAT-011 sets up the framework and coverage floors. S1 adds a minimal Vitest config that extends the config package (TBI-003). FEAT-011 raises it to the 80/75 floors.

**Tooling and layout**

- **Package layout**: `templates/full-stack-express/packages/contracts/`. The package name uses the documented placeholder, written `@scope/contracts` here. It is ESM-only with an `exports` map and `"sideEffects": false`. It ships three entry points: the root barrel, `./openapi` (the pure document builder), and `./openapi.json` (the committed file). Node-only scripts (file writes, Prettier, diff) live under `scripts/` and are not exported, so the web bundle stays free of Node built-ins.
- **Committed document path**: `packages/contracts/openapi/openapi.json`.
- **Script names**: `openapi:generate` and `openapi:check` in the contracts package, with root aliases of the same names. The root `check` script runs `openapi:check`. FEAT-002 lists install, build, check, test, run, migrate, and seed; these two extend that list and go in the README. FEAT-012 references `openapi:check` as the drift gate.
- **Deterministic output**: The builder sorts `paths` and `components.schemas` by key and orders operations by a fixed method list. Property order inside a schema follows the authored order. `info.version` is a constant in the contracts source, not read from `package.json`, so a version bump does not cause drift. The generator formats the JSON with Prettier using explicit options (`parser: "json"`, `printWidth: 80`, `tabWidth: 2`) that match Apex's root `.prettierrc`. Apex's root `npm run lint` (`prettier --check .`) then accepts the file whichever config Prettier picks. The pinned lockfile fixes the Prettier version.
- **Drift check semantics**: Generate in memory, compare bytes with the committed file, and print a unified diff on mismatch. The same command then validates the committed file as OpenAPI 3.1. It exits non-zero on either failure.
- **Express route discovery (design for FEAT-006)**: `apps/api` mounts every handler through one `registerRoute` helper on one flat router. An ESLint rule bans direct `get`, `post`, `put`, `patch`, `delete`, and `all` calls on `app` and `router` in `apps/api/src`. `routes:check` reads the router's route list and calls `compareRouteInventory`. The check throws if it finds zero routes, so a change in Express internals fails loudly instead of passing. Risk: Express 5 router internals shift in a minor release; the pinned lockfile and the zero-route throw contain that.

**Inherited from the PRD**

- **Root formatting**: The PRD asks the template to match Apex's formatting rules or get an approved ignore entry. For this Feature, the generator's fixed Prettier options remove the question for `openapi.json`. The wider decision stays with TBI-001.
- **`templates/` and the codemap**: The `codemap-sync` rule asks for a `.cursor/CODEMAP.md` entry when a top-level folder appears. TBI-001 creates the folder and owns that entry. The codemap check only verifies roots it lists, and `templates/` is not among them.
- **Apex CI treats template files as application changes**: `scripts/ci/is-markdown-only-changes.mjs` gates the markdown-only shortcut, and `.ts` and `.json` files are not markdown. The PR for this Feature therefore runs the full Apex suite and dev deploy. Apex's `tsconfig.server.json`, `tsconfig.client.json`, `jest.config.js`, and ESLint script cover only `src/**`, so none of them reads the template.
- **Prior art in Apex**: Apex pairs a shared Zod schema with `z.infer` (`CreateSessionRequestSchema` in `src/shared/types/calendarWorkItemAssistant.ts`, parsed with `safeParse` in `src/server/routes/api.ts`). It has no route-level definitions, no OpenAPI, and no Problem Details. This Feature extends the pairing pattern; it does not copy an existing contract module.
- **No Apex RBAC**: BR-003 and BR-008 keep Apex's `requirePermission` and `can()` patterns (`rbac-governance.mdc`) out of the template. The contract declares only whether a route needs an authenticated principal.
