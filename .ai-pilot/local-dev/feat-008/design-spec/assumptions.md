## Unresolved Items

Items that could not be inferred from the PRD, backlog, or codebase. Each must be decided before the relevant implementation step starts.

- ⚠ **TBI-019 dependency gap**: FEAT-008 depends only on FEAT-001, and TBI-019 has `dependsOn: []`. But TBI-019 lists "Typed configuration" as a technical dependency (TBI-004 in FEAT-002), and PBI-016 scenario (b) requires a log line, which needs the Pino logger (TBI-016 in FEAT-007). The adapter and its unit tests (S1–S3, S7) need neither, so they can start at once. Steps S4 (env schema entry) and S5 (composition-root wiring) cannot finish until TBI-004 and TBI-016 exist. **Decision needed:** add `TBI-004` and `TBI-016` to `TBI-019.dependsOn` in the backlog (recommended), or accept that S4 and S5 land as a follow-up commit after FEAT-002 and FEAT-007.
- ⚠ **Flag provider decision is open**: The backlog lists "Feature-flag provider decision (open)" as a dependency, and the PRD names the provider as an unresolved extension point. The v1 interface is boolean, synchronous, and takes no evaluation context. A provider that needs a user or tenant context, non-boolean variations, or asynchronous start-up may force a signature change. Adding an optional third parameter to `isEnabled` later stays source-compatible for call sites, but a provider that needs async initialisation would need a change at the composition root. **Decision needed:** Platform Engineering confirms the provider's evaluation model when it picks one. Until then the interface stays as specified.

## Assumptions Accepted

Inferences made during synthesis that were treated as resolved. Confirm these with stakeholders before implementation locks.

- **Output file names**: The kickoff instructions fix the file names as `design-doc-design.md`, `design-doc-tech-spec.md`, and `design-doc-assumptions.md` in `.ai-pilot/output/`. These replace the skill's `{feature-slug}-*.md` pattern and the `{slug}-design-spec/` sub-folder. Risk: a downstream tool that expects the skill's folder layout does not find the files.
- **Template location and member names**: The PRD fixes `templates/full-stack-express/` and five workspace members (web, API, contracts, UI, config) but not their directory names. This spec uses `apps/api`, `apps/web`, and `packages/*`. Derived from the usual pnpm layout. Risk: TBI-001 picks other names, and every path in the tech spec needs a find-and-replace.
- **Server-side only**: The interface lives in the API application. There is no web hook, no `/api/v1` endpoint that returns flag values, and no entry in the contracts package. Derived from the PBI-016 persona (Developer), the out-of-scope list (no administration screens), and the API contract rule that every endpoint appears in Zod route definitions. Risk: a team that wants client-side gating must add a contract endpoint and a hook later.
- **Boolean flags, no evaluation context**: `isEnabled(name, defaultValue)` returns a boolean. No user, group, or tenant argument. Derived from PBI-016 out-of-scope ("Per-user or per-group targeting") and the TBI-019 description ("a named flag with a default value"). Risk: see the provider ⚠ above.
- **Default declared at the call site**: The "declared default" in the acceptance criteria is the `defaultValue` argument each call passes. There is no central flag registry. Derived from the TBI-019 description. Risk: two call sites can declare different defaults for one flag name. Reviewers catch this, and the module map tells developers to hoist the name and default into one constant.
- **Configuration source**: One optional environment variable, `FEATURE_FLAGS`, holds a JSON object that maps flag names to booleans, for example `{"checkout-v2":true}`. The PRD says only "reads flag values from configuration". JSON gets a single strict Zod parse. Risk: `.env` and Docker Compose quoting is awkward for JSON, so the README must show single-quote wrapping. Platform Engineering may prefer a different variable name or format.
- **A bad flag value does not abort startup**: `FEATURE_FLAGS` is optional in the environment schema, and its value is validated by the adapter, not by startup validation. BR-010 aborts startup for a missing or invalid required value, but PBI-016 scenario (b) requires the adapter to return defaults and log. The scenario wins because the variable is not required. Risk: a typo in production configuration shows up as a log warning, not a failed start.
- **All-or-nothing parsing**: If the JSON is invalid, or any key or value has the wrong shape, the adapter ignores the whole value and every flag returns its declared default. It does not keep the valid entries. A partial result would make a half-applied rollout hard to see. Risk: one bad entry turns off unrelated flags that were on.
- **Absent or empty configuration is not a problem**: An unset variable, an empty string, or whitespace is treated as "no flags defined". Nothing is logged. Only a non-empty value that fails to parse logs.
- **Kebab-case names**: Config keys must match `^[a-z0-9]+(-[a-z0-9]+)*$`. Derived from the key convention in Apex's `featureFlagService.ts` (`KEBAB_CASE_RE`) and the `feature-flags` skill. The pattern is copied, not imported, because the template holds no Apex code (BR-008). It also blocks prototype-pollution keys such as `__proto__`. Risk: a project that wants other characters changes one regular expression.
- **Log once, at construction**: The adapter parses the value once when the composition root builds it, and logs one warning if parsing fails. It does not log on every evaluation. PBI-016 (b) says "logs the problem" when code evaluates a flag. This spec reads that as "the problem is logged, and evaluation returns defaults". Risk: a reviewer who expects one log line per evaluation sees fewer lines. The test arranges construction and evaluation together, so both readings pass VT-04.
- **Values are fixed for the process lifetime**: The adapter reads configuration once and never reloads it. Changing a flag means changing the environment and restarting the instance. Derived from the TBI-019 non-functional requirement (evaluation never waits) and the graceful-shutdown behaviour in FEAT-007. Risk: a team that wants live toggling needs a provider adapter.
- **Logger is injected through a small interface**: The adapter takes a `FlagLogger` with one `warn(fields, message)` method. A Pino logger satisfies it with no wrapper. This keeps the module free of a Pino import, so TBI-019 can be built before TBI-016. Risk: none beyond the dependency ⚠ above.
- **Log payload carries no configuration text**: The warning holds the event name, the variable name, and a reason code (`invalid_json` or `invalid_shape`). It never holds the raw value or Zod issue paths, because a key could look like an identity value (BR-007). Risk: less detail when debugging. The README tells developers to validate the JSON locally.
- **No reference call site**: The reference profile and health endpoints do not read any flag, so the template ships no sample flag that changes behaviour. Tests supply the gated behaviour. The composition root receives the evaluator so route factories can use it. Derived from the existing-code protection rules and from "ship no behaviour change to the reference feature". Risk: developers have no live example. The module map and the developer skill carry a code snippet.
- **Apex's cleanup markers are not adopted**: The `@feature-flag:<key>` comment contract belongs to Apex's `feature-flags` and `feature-flag-cleanup` skills. The template ships its own five role skills and holds no Apex content. Risk: automated flag cleanup does not work on generated applications until a project adds its own convention.
- **Vendor-SDK guard is a deny list**: The test fails when any `package.json` in the template workspace names a known vendor flag SDK (LaunchDarkly, Unleash, Flagsmith, GrowthBook, Split, ConfigCat, Statsig, PostHog). OpenFeature is not on the list, because it is an open specification that a future adapter may wrap. Risk: a new vendor SDK that the list does not name passes the test. The `package.json` review in code review is the second check.
- **Coverage floors apply**: The new module must meet the template floors of 80% lines, functions, and statements and 75% branches (BR-012). The module is small, so the tests target 100% of branches.
- **Documentation hand-off**: The module map entry, the `FEATURE_FLAGS` row in the README, and the register entry for the flag provider are authored in FEAT-014 and FEAT-017, which run in a later phase. This Feature supplies the text in step S8. The documentation validator (TBI-034) reports a module without a map entry, so S8 must land before that validator runs on the finished template.
- **Persona mapping**: Developer is the only actor. Platform Engineering (mapped to Platform Admin in the backlog) owns the later provider choice but takes no action in this Feature.
- **PBI-016 scenarios**: The backlog gives four acceptance criteria: enabled, unreadable configuration, unknown flag, and adapter replacement. The skill needs a negative scenario, so scenario (d) comes from the PBI-016 security requirement ("never taken from request input"). The adapter-replacement criterion is kept as scenario (e). Risk: none; both trace to the backlog.
- **No Apex Feature Flag**: The PRD sets "Flag required: No". Nothing in this Feature calls Apex's `isFeatureEnabled`, the `useFeatureFlag` hook, or Platform Admin → Feature Flags. The template's interface is a capability of generated applications and is separate from that system.
