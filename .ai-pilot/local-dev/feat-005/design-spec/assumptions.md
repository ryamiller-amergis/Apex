# Assumptions & Unresolved Items — Remaining Work Loop-Back to My Work

> **PRD slug:** `start-cloud-development-from-my-work` | **Priority:** Should Have | **Feature flag:** `my-work-cloud-agent`
> Shared between [design-doc-design.md](design-doc-design.md) and [design-doc-tech-spec.md](design-doc-tech-spec.md).
> Resolve all ⚠ items before implementation begins.

---

## Unresolved Items

- ⚠ **Incomplete-AC signal shape from the Cloud Agent completion payload**: The PRD's Webhook completion receiver (FEAT-001/TBI-001) hands "status, PR URL, branch, and summary" to the run lifecycle's terminal write, but no field on that payload is named as a structured list of unmet acceptance criteria. TBI-007's definition of done still requires "incomplete acceptance criteria" as one of the three leftover-work leaves. This blocks the exact input contract of `computeLeftoverWork()` (§Data and Contracts in the tech spec). **Decision needed:** confirm with the FEAT-001 webhook-payload owner whether the Cloud Agent emits a structured `incompleteAcceptanceCriteria: string[]` sub-field on completion, or whether Apex must parse it out of the freeform `summary` text. This design assumes the former (a structured sub-field) and flags the field as optional/absent-tolerant so nothing breaks if the vendor payload omits it.
- ⚠ **Append-vs-update semantics for the ADO leftover-work comment across repeat Resume cycles**: When a Developer resumes a session multiple times, each terminal run can produce its own leftover-work summary. The PRD does not say whether Apex should post one discussion comment per finished run (append) or edit a single running comment in place. Editing in place requires storing an ADO comment id on the session; appending does not. **Decision needed:** confirm the desired ADO discussion UX. This design defaults to **append a new dated comment per terminal run** (§Architecture and Approach, TBI-007) because it needs no new persisted ADO identifier and matches how `addWorkItemComment` is already used elsewhere in `azureDevOps.ts` as a one-shot write, not an editable thread.

## Assumptions Accepted

- **Leftover work is a new nullable column on the existing session table, not a new table or ADO field**: The epic-level assumption for "Cloud Agent Run Outcomes" states remaining issues are "a structured leftover-work summary attached to the existing run and work item, not a new work-item type or a new Azure DevOps field," and BR-007 rules out child ADO items. Derived: add one nullable `leftover_work` jsonb column to `dev_sessions` (additive migration, same pattern as TBI-001's session extensions) rather than a new control-plane table. Risk if wrong: a new table would duplicate the current-run pointer TBI-001 already owns and fragment the read path the row polls.
- **ADO write-back uses the existing discussion/comment path (`AzureDevOpsService.addWorkItemComment`), not a new custom field**: Follows directly from the same epic-level assumption above and from BR-006/BR-008's pattern of reusing existing ADO write primitives (`addWorkItemHyperlink` for the PR URL) rather than inventing new ones. Risk if wrong: a custom field would need an ADO process/template change outside Apex's control, which the PRD's Out of Scope section (no full ADO PR lifecycle, no new field) forecloses.
- **A fully clean run writes nothing to ADO**: PBI-008(c) requires "no leftover work is shown" when a run finishes with a PR and all checks passed; TBI-007's DoD is silent on whether a clean run should still post an affirmative ADO comment. Derived: `leftoverWork` persists as `null` and `addWorkItemComment` is never called for a clean run, to avoid discussion-thread noise on every successful run. Risk if wrong: some teams may want an explicit "all clear" comment for audit trail; this can be added later without a schema change since it only changes when the write fires, not what is stored.
- **Resume clears stale leftover work at enqueue time, not at read time**: PBI-005 (FEAT-002) establishes that a new run enqueued via Resume keeps the prior run in history while the session's live-state fields move to reflect the new run. Derived: the same Start/Resume enqueue step that will reset `prUrl`/check-result fields for the new run also resets `leftoverWork` to `null`, and TBI-007's computation only runs again once the new run reaches a terminal state. Risk if wrong: a Developer could see last run's stale "leftover work" persist while a new run is already in flight, contradicting BR-004's "no run" states.
- **TBI-007 is a pure composition step over already-decided data, not a new source of truth**: TBI-007's own `technicalDependencies` list TBI-005 (check-result capture) and TBI-006 (PR-status computation) — both owned by other Features (FEAT-003, FEAT-004) in this PRD. Derived: `computeLeftoverWork()` reads the session's already-materialized `checkResults` and PR-status fields rather than re-querying the git host or re-running checks itself. Risk if wrong: duplicated PR/check lookups would double the read cost the PRD's NFR already budgets to "the same session read that already returns the current-run projection."
- **ADO writes for leftover work reuse `retryWithBackoff` (`src/server/utils/retry.ts`)**: TBI-006's own NFR requires the ADO PR-URL write to retry on transient failure rather than being dropped silently, and this codebase already centralizes that behavior in `retryWithBackoff` (used by `askApexService.ts` and covered by `retry.test.ts`). Derived: the leftover-work ADO comment write wraps `addWorkItemComment` in the same utility instead of a bespoke retry loop. Risk if wrong: a bespoke retry would duplicate tested backoff/jitter logic for no behavioral gain.
