## Unresolved Items

Items that could not be inferred from the PRD, backlog, or codebase. Each must be decided before the relevant implementation step starts. Each item names a default. The specs use that default until the team decides otherwise.

- ⚠ **Backlog `route` value on FEAT-013 is wrong**: The backlog gives this Feature the route `/profile/licenses/edit`. This Feature has no screen. The PRD Target Surface says the template "has no Apex navigation entry", and Apex already owns `/profile` (User Profile). Left as is, the value could make a reader think the Feature changes an Apex page, which BR-008 forbids. **Decision needed:** confirm the Feature has no route and correct the backlog value to `Component` (the value FEAT-002 and FEAT-012 use for work with no screen). **Default used:** no route; UI/UX is "Not applicable". **Blocks:** nothing in implementation. It affects the ADO export and the design-doc validation score.

- ⚠ **Organization-approved tool and base-image set is not available**: TBI-030, TBI-031 and TBI-032 all say tools come from the "organization-approved set", and no list exists in the PRD or the repository checkout. This blocks choosing the secret scanner, vulnerability scanner, license checker, SBOM generator and the pinned Node base image. **Decision needed:** Platform Engineering names the approved tools and the approved Node image (registry and digest policy). **Default used:** these candidates, each pinned in the lockfile or compatibility table:
  - Secrets: `secretlint`, an npm package pinned by the lockfile.
  - Vulnerabilities: OSV-Scanner on `pnpm-lock.yaml`.
  - Licenses: `pnpm licenses list --prod --json`, which needs no extra dependency.
  - SBOM: CycloneDX JSON from `@cyclonedx/cdxgen`.
  - Base image: `node:<LTS major>-bookworm-slim`, pinned by digest. `runners/load-test-k6/Dockerfile` already uses this family.
  Implementation step S1 records the final choices in the compatibility table.

- ⚠ **Container-to-app contract names are undefined**: The container needs four settings that FEAT-002 (typed configuration), FEAT-005 (identity adapter) and TBI-014 (composition root) own, and none of them has a name in the backlog: the production signal, the authentication mode, the built-client directory and the listen port. A fifth problem: the only authentication mode the backlog defines is `development`, and it aborts in production. A production container with no identity provider therefore has no valid mode to start in. PBI-027 (a) asks the running container to pass liveness and readiness. **Decision needed:** (1) confirm the variable names, and (2) confirm which environment value the smoke test uses. **Default used:** working names `APP_ENV` (`local` | `production`), `AUTH_MODE`, `WEB_DIST_DIR`, `PORT`. Smoke test (a) runs the image with `APP_ENV=local` and `AUTH_MODE=development`, and PBI-027 (d) runs it with `APP_ENV=production` and `AUTH_MODE=development`. The image is identical in both runs. **Blocks:** S8 and S9.

- ⚠ **Vulnerability severity threshold and exception record format are undefined**: PBI-029 says a "reviewed exception recorded in the repository" is honored. It does not say which severities fail the scan, what an exception contains, or whether it expires. **Decision needed:** confirm the threshold and the record fields. **Default used:** fail on `high` and `critical`. An exception needs `advisory`, `package`, `reason`, `owner`, `reviewed` (date) and `expires` (date). An expired exception is not honored and is reported. This mirrors the quality-manifest rule in TBI-027 that a deferral needs a reason and an owner. **Blocks:** S2 and S3.

- ⚠ **No way to run migrations from the production image**: BR-006 says Platform Engineering runs migrations as a separate deployment step. TBI-032 requires the runtime image to hold only production dependencies. The migration tooling (`drizzle-kit` or a SQL runner) is normally a development dependency, so the image cannot run migrations as specified. **Decision needed:** either (a) Platform Engineering runs the template's `migrate` script from a checkout in the pipeline, or (b) the image ships a small production-dependency migration runner and the SQL files. **Default used:** (a). The image holds no migration tooling and no SQL files, and the handoff document (FEAT-017) names the `migrate` script as the contract. **Blocks:** S8 only if the answer is (b).

- ⚠ **Apex root formatting check covers the template**: Apex's `npm run lint` runs `prettier --check .` over the whole repository, using the root `.prettierrc` (single quotes, `es5` trailing commas, 80 columns). Template Markdown, JSON and YAML, including the new config files and runbook, are in its reach. The PRD already lists this as an open assumption. **Decision needed:** make the template conform to the root rules, or have the maintainers approve a minimal `.prettierignore` entry for `templates/full-stack-express/`. **Default used:** conform. This feature adds no ignore entry. **Blocks:** S10. VT-23 runs the check.

- ⚠ **Whether supply-chain scripts are quality-manifest gates**: The PRD lists the manifest gates: build, type-check, lint, formatting, OpenAPI drift, migration validation, unit, component, API, integration, accessibility and container build. Secret scan, vulnerability scan, license check and SBOM are not in that list. The epic success metric says each of them "runs from a script". Also, FEAT-012's rule that each manifest gate "names an existing script" means `container:build` must exist under the exact name the manifest uses. **Decision needed:** confirm whether the four supply-chain scripts become manifest gates. **Default used:** no. Only `container:build` is a gate. The four supply-chain scripts are listed in the handoff document as scripts Platform Engineering consumes. **Blocks:** S10, the step that reconciles script names with FEAT-012.

## Assumptions Accepted

Inferences made during synthesis that were treated as resolved. Confirm these with stakeholders before implementation locks.

- **Persona mapping**: Platform Engineering maps to `Platform Admin`, and template consumers and Apex-launched development agents map to `Developer`. This follows the PRD "Assumptions Made" and the backlog persona list. **Risk:** low. Only labels would change.
- **Single-prompt-build ADR**: The ADR text was not in the checkout. This Feature depends on it only through the epic's "gates as scripts" model. **Risk:** low.
- **Template location and layout**: The Feature adds files only under `templates/full-stack-express/`. It assumes the layout `apps/api`, `apps/web`, `packages/contracts`, `packages/ui`, `packages/config`, `scripts/`, `config/` and `docs/runbooks/`. The backlog names modules but not directories. **Risk:** medium. Path references in the specs and Dockerfile must be rechecked against FEAT-001 output.
- **Apex stays untouched**: The Feature changes no file in `src/`, `migrations/`, root `package.json`, `.gitignore`, `.dockerignore` or `.github/`. This follows BR-008 and `scope-discipline.mdc`. The root `.dockerignore` is written for repo-root builds (the k6 runner) and does not apply to a build whose context is the template folder, so the template gets its own `.dockerignore` and `.gitignore`. **Risk:** low.
- **Node version**: The runtime Node major comes from the template's compatibility table (FEAT-001). It is assumed to be the current LTS, 24, which matches Apex's `.nvmrc`. **Risk:** low.
- **Script names**: `scan:secrets`, `scan:vulns`, `scan:licenses`, `scan` (runs all three and reports every finding), `sbom`, `container:build`, `test:container`. FEAT-001 sets the naming style (install, build, check, test, run, migrate, seed). **Risk:** low. Names must match what the quality manifest and handoff document cite.
- **Script implementation**: Scripts are Node `.mjs` files with no build step, called by named `package.json` scripts. This follows the Apex pattern (`lint:codemap` runs `scripts/ci/check-codemap-paths.mjs`). **Risk:** low.
- **Exit codes**: `0` means no findings, `1` means findings, `2` means the check could not run (missing lockfile, malformed config file, advisory source unreachable, Docker daemon absent). A check that cannot run never reports success. **Risk:** low.
- **Secret scan scope**: It scans tracked working-tree files, not git history. The template moves into a new repository, so its history is not the history that matters. Findings print file, line and rule name only, never the matched value. **Risk:** medium. Platform Engineering may want history scanning in the pipeline.
- **Planted secret is created at test time**: TBI-030 requires proof that a planted fake secret is detected. A committed fake secret would make the repository fail its own scan. The test writes the fake secret to a temporary directory at run time, and it builds the token by concatenation so no complete token appears in source. **Risk:** low.
- **Vulnerability scan scope**: It covers dependencies from the lockfile, production and development. It does not scan operating-system packages in the image; the registry scan owned by Platform Engineering does that. Unit tests feed recorded advisory reports, so they run offline. The real scan needs network access to the advisory source. **Risk:** medium.
- **License check scope**: It checks production dependencies against `config/supply-chain/allowed-licenses.json`. A license identifier not on the list is reported with the package name. **Risk:** low.
- **SBOM format and scope**: CycloneDX JSON, written to `artifacts/sbom/`. It lists the production dependencies of the API and web packages, since web dependencies are bundled into the shipped client. Development-only dependencies are excluded. The file is deterministic: components sorted by package URL, `serialNumber` derived from the lockfile hash, and no wall-clock timestamp (`SOURCE_DATE_EPOCH` is used if set). `pnpm sbom -- --image <tag>` adds an image-contents mode, which TBI-031 asks for. **Risk:** medium. Platform Engineering may require SPDX.
- **SBOM output is ignored by Git**: The template's own `.gitignore` excludes `artifacts/`. The write is atomic: a temporary file is renamed on success and removed on error. **Risk:** low.
- **Image shape**: Multi-stage build (`base`, `build`, `prod-deps`, `runtime`). The runtime stage has Node only. It removes `npm`, `npx`, `corepack` and `yarn`, and has no `pnpm`. It runs as numeric UID `10001`. **Risk:** low.
- **Image holds no migration or seed code**: The container never changes schema at startup (BR-006). The seed command (synthetic local data only) stays out of the image. **Risk:** low.
- **Health check in the image**: The Dockerfile has a `HEALTHCHECK` that calls `/health/live` with Node's built-in `fetch`. It uses liveness only, so a database outage does not mark the container unhealthy. Platform Engineering can override it. This is a generic Docker feature, not an ECS assumption. **Risk:** low.
- **Hardening is tested**: The smoke test also runs the image with `--read-only` and `--cap-drop ALL`. This assumes the API writes nothing to disk (Pino logs go to stdout). **Risk:** medium. If the API needs a scratch directory, the test adds a `tmpfs` mount and notes it in the runbook.
- **No registry or cloud names**: The build tags the image `<service-name>:local`. No script pushes an image, and no file mentions AWS, ECS or ECR (BR-014). **Risk:** low.
- **Docker is a local prerequisite**: Docker Compose is already required for local PostgreSQL (FEAT-002), so `container:build` and `test:container` assume a Docker daemon. If it is absent, they exit `2` with a message naming Docker. **Risk:** low.
- **Dependency-update automation**: Out of scope, as the PRD assigns it to Platform Engineering. **Risk:** low.
- **No new Apex permission, flag or migration**: The Feature adds none. It consumes `/health/live`, `/health/ready` and static serving from FEAT-006 and TBI-014. **Risk:** low.
